# Поиск международных концертов, фестивалей и стендапа

Это общий workflow для `activity-recommendations` и музыкальных запросов `digest`.
Список площадок существует **только в Personal Radar Knowledge**, не копировать его
в skill, промпты SQLite, seed приложения или отдельный scraper. Редактирование этого
workflow не запускает поиск, sync или публикацию.

## Каталог и порядок

1. Перед сбором прочитать актуальные `settings.prompts.concerts`, period/timeZone
   и revision через `/api/recommendations?scopeId=belgrade&kind=concerts-2026` (либо
   week); профиль, артистов, feedback-summary и query-summary — штатными API.
   Для digest первичен текущий запрос; периоды digest сохраняют собственную семантику.
2. Проверить уже имеющиеся события. Для Afisha.rs сначала облачный MCP по
   [общему сценарию](afisha-fallback.md), локальный sync — только при его Afisha HTTP 403.
   Остальные нужные агрегаторы (AllEvents, Tickets.rs и др.) обновить штатно;
   сегодня успешный, но слишком узкий диапазон не доказывает годового покрытия.
3. Полностью прочитать допустимые Telegram-каналы из действующей коллекции,
   с локальными исключениями и сохранением raw/checkpoints. Площадки дополняют,
   а не сокращают это покрытие.
4. `GET /api/recommendations/sources?scopeId=belgrade`: `venues` содержит площадки
   и организаторов из `belgrade-live-venues` / `belgrade-live-organizers`.
   Проверить `warning`, `venueWarning` и `knowledgeRevision`. Пустой массив с
   warning не означает отсутствие концертов или успешно проверенные источники.
5. Для источников с `venue.afishaVenueUrl` использовать облачный Afisha reader
   по [контракту ниже](#afisha-по-площадке), затем дополнить Web Search.
   Сначала проверить все P1-площадки, затем P2 под профиль и международные туры,
   далее P3/сезонные, площадки с `standup` и организаторов. `venue.kind=organizer`
   — организатор на разных сценах; не использовать его имя как место концерта.
   Метаданные источника: aliases, searchDomains, priority, eventTypes, genres,
   pageType, calendarAvailability, checkedOn, pages. Приоритет — порядок исследования,
   не персональный score и не автоматическое включение каждого выступления.
6. Подтвердить отобранные находки на первичных страницах артиста, организатора,
   площадки и уполномоченных билетных страницах. Одна выдача агрегатора не заменяет
   поиск по площадкам. Для годовой вкладки покрыть оставшиеся месяцы до конца 2026,
   а не только ближайшую неделю. Для недельной — использовать тот же каталог в её датах.

Если API недоступен, возвращает `venueWarning` или запущенная старая версия
ещё не возвращает `venues`, не считать каталог пустым: использовать локальный
fallback ниже либо разрешить обе коллекции Personal Radar retrieval с
`include_details=true` и пагинацией (`next_offset`, тот же commit); полные поля
лежат в `results[].details`, при `details_omitted` читать отдельный source record. Локальный fallback: прочитать manifest,
**все** `datasets.collections.paths` в объявленном format, найти коллекции и их
разрешённые `members`; затем все `datasets.sources.paths`, сопоставить IDs и читать
полные `record_path` JSON. Краткий source index не содержит всей metadata/summary.
Фильтр: enabled=true, platform=web, domain activities, соответствующая роль
venue_event_discovery / organizer_event_discovery, metadata.country=Serbia,
metadata.city=Belgrade, access.method=web_search. Не брать другие города и disabled.
Индексатор уже разрешает filters/alias коллекций; не изобретать собственные фильтры
на YAML. Локальное чтение не требует GitHub fetch или catalog-sync pull в SQLite.

## Матрица запросов

Взять название/aliases, домены и дополнительные ссылки из текущих карточек каталога.
Подставлять фактический год/месяц/период, RU/EN/SR варианты Belgrade / Beograd / Белград.
Разбить дальний горизонт по месяцам, чтобы ближайшие анонсы не вытеснили остальные.
Для каждой площадки сочетать несколько направлений, учитывая историю эффективности:

- `site:<searchDomain> "<venue>" <month> <year> concert`;
- `"<venue alias>" Beograd <month/year> koncert strani bend`;
- `"<venue>" Belgrade <year> "world tour"` / `"European tour"` / `"international artist"`;
- `"<venue>" <month/year> <profile genre> live` (indie, postpunk, darkwave, rock,
  jazz, electronic и т. п. выбирать по текущему профилю, не считать этот пример вкусом);
- `"<artist from profile>" Belgrade <year> official tour`, затем `<artist> <venue>`;
- `"<venue>" <month/year> <язык из профиля> stand-up` / `гастроли` / `comedy tour`;
- `"<organizer>" Beograd <month/year> concerts festival international`;
- `Belgrade <month/year> music festival lineup international`, а также food/wine
  festival по действующему concerts-промпту; не сужать все фестивали до музыки.

`site:` сначала применять к домену, а не жёстко к одному устаревшему URL календаря.
Для общих доменов (Afisha, Instagram, RA, Tickets) обязательно добавлять venue/alias;
городская афиша RA не является персональным календарём одной площадки.
Дату публикации/индексации не подменять датой выступления: старый анонс может
вести на будущее событие. Не ставить recency, отсекающий такие анонсы.
Неизвестный охват/пагинацию отмечать; нулевая выдача одного запроса — слабое свидетельство.

## Доступ и подтверждение

`official_calendar` — официальная афиша; `official_social` — соцсеть площадки;
`aggregator_listing` / `ticketing_listing` — сторонняя афиша / билеты;
`venue_info_only` — справка, новости или link hub. Наличие ссылки в Knowledge
не означает, что её полная программа сейчас прочитана. `checkedOn` фиксирует
предыдущую проверку, а не текущий live-run. Статус `search_only`, `limited`,
`unavailable`, `links_only`, `info_only`, `news_only`, `city_listing` требует
поиска конкретных анонсов, билетов/организаторов и явного учёта пробела.

Для динамической страницы использовать существующий безопасный browser/read
workflow; не обходить CAPTCHA, login/429 или ограничения сайтов. Официальный
Instagram может быть подтверждён ссылкой справочника, но оставаться непрочитанным.
Не обещать официальную веб-афишу по одной агрегаторной карточке. При отсутствии
официального календаря не изобретать его; для сезонной площадки искать организаторов.
Не добавлять Songkick API, scraper, новые платные API или расписания.

Проверить headliner и весь lineup, реальный жанр и формат, точный зал/адрес,
даты сеансов, год, переносы/отмены и язык **конкретной программы**. Организация,
анонсирующая событие, может отличаться от фактического зала. Трибьюты/каверы
не равны оригинальным исполнителям. Иностранный DJ в реальном lineup важнее
общего слова international в описании клуба; не импортировать все вечеринки.
Программы на языках пользователя допустимы по актуальному профилю. Национальность и алфавит имени не доказывают
язык; неизвестный язык оставить `unknown` в evidence/validation notes и обозначить
существенную неопределённость, не расширяя схему snapshot новым полем.
Следовать текущим пользовательским критериям и ai-events-review; этот workflow
не вводит абсолютный фильтр гражданства и не меняет промпты SQLite.

## Защита состояний и покрытие

До передачи подробностей кандидатов в LLM выполнить deterministic
`/recommendations/filter-candidates` по [основному контракту](workflow.md#скрытые-события-до-llm-анализа).
Сохранить raw отдельно; затем review/scoring/import через digest. Дедуплицировать
один сеанс между venue/организатором/агрегатором, сохраняя provenance;
другие даты того же концерта — отдельные сеансы, не блокировать их одним скрытием.
Не менять hidden, favorites, personal entries, skip/dislike или старые snapshots.

В существующих receipts ai-mcp-discovery записывать реальные query и известную
отдачу (неизвестные метрики null); обновить query-summary после batches. Не создавать
параллельный журнал. В runtime-файле текущего запуска вести покрытие source ID ×
месяц × направление: прочитано / частично / недоступно / исключено; отмечать запросы,
проверенные ссылки, дату проверки и оставшиеся пробелы. Не выдавать планируемый запрос
за выполненный или успех HTTP без карточек за просмотренную афишу.

Перед сохранением рекомендаций перечитать настройки/revision/period, повторить
фильтр скрытого/прошедшего; публиковать только штатным POST нового snapshot и
проверить GET. Семантика week (сегодня–воскресенье), concerts-2026 (будущие до
31 декабря 2026), scopeId=belgrade и Europe/Belgrade остаётся прежней. Сам каталог
и шаблоны запросов независимы от года. В notes/отчёте явно перечислить недоступные
площадки и месяцы с неполным покрытием. Не объявлять годовую подборку полной
по нескольким находкам агрегаторов.


## Afisha по площадке

Для `venue.afishaVenueUrl` использовать облачный `afisha_read_events_batch` с
`sections[].venueUrl`, целевыми разделами и датами по [общему сценарию](afisha-fallback.md).
Переиспользовать уже полученные общие карточки; отдельный venue read нужен для
дополнения или проверки, а не повторного получения тех же данных. Проверенная
блокировка облачного Afisha за этот проход действует и для площадок: не запускать
новую серию запросов на каждую venue. Локальный sync допускается только после
Afisha HTTP 403 облака и один раз за проход. Если он уже отработал, использовать
результат; при оставшихся пробелах продолжить hosted Web Search и первичные
страницы организаторов/площадок/билетных сервисов.

Отсутствие облачного tool не блокирует поиск по площадкам: раскрыть ограничение
и перейти к web, без предварительного локального Afisha sync. Для чтения найденных
доступных страниц можно использовать `activity_web_read`; не повторять уже
заблокированное чтение, не угадывать term IDs и не считать старые объявления будущими.
Данные проходят фильтр скрытого до персонального анализа, затем review/import и
дедупликацию с общим сбором и Telegram. Статус venue read включать в отчёт Afisha.

Правила языка и широкого включения программы читать только из
`profile.additionalPreferences` и `profile.recommendationPrompts`. Здесь нет
обязательного приоритета русского языка или отдельного списка вкусов.
