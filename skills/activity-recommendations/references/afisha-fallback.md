# Afisha.rs: резервный сбор при HTTP 403

Применять при формировании рекомендаций или дайджеста, если штатный sync Afisha.rs
завершился HTTP 403, включая Cloudflare challenge. Проверить фактическую ошибку
последней попытки; 403 другого источника не включает это правило. Не повторять
заведомо заблокированный запрос в цикле. Обычный технический sync сам не запускает
Telegram или LLM Web: резервный сбор выполняет модель в рамках текущей подборки.

## Разделить период

Определить `today` по текущим часам в `Europe/Belgrade` и сравнивать календарные
даты, не UTC-день. Для объединённого периода запрошенных вкладок:

- если период включает today, покрыть текущий день официальным `@afishars`;
- будущую часть от `max(начало периода, завтра)` до конца периода покрыть
  усиленным web search с фокусом на Afisha.rs;
- для запроса только будущих дат не добавлять сегодня и не выполнять отдельное
  чтение канала ради сегодняшней подборки. Обычный полный обход Telegram остаётся.

Сохранённые карточки Afisha и ранее прочитанные raw-анонсы остаются дополнительным
материалом с исходной датой проверки. Не объявлять их свежей синхронизацией.
Другие агрегаторы, включая Tickets.rs и AllEvents, и общий поиск продолжаются.
Для географий вне покрытия Afisha.rs использовать их scoped источники.

## Сегодня: официальный Telegram

Разрешить Knowledge source `telegram-afishars`: `https://t.me/afishars`, подтверждённый
numeric channel ID `1886741665`. Сверить актуальные enabled/access и локальные
исключения. `@afisha_rs` с подчёркиванием — другой источник и не заменяет этот канал.
Отключение/недоступность раскрыть как пробел, не менять подписки и Knowledge.

Использовать общий monitoring batch и сохранённые raw-снимки; не перечитывать уже
полученные сообщения без необходимости. Проверить публикации за вчера и сегодня:
сегодняшний дайджест мог выйти вчера под заголовком «Планы на завтра». При старом
checkpoint дочитать новые сообщения и восстановить нужное окно из raw; если его
нет или требуется проверить правки, перечитать это окно с обычными фильтрами и
пагинацией. Не сужать глобальное чтение всех каналов до этих двух дней.

Разбирать все продолжения подборок, а не только первый пост. Дату события брать
из заголовка/анонса; дату публикации не подставлять вместо неё. Связывать части
подборки по подтверждённому заголовку и последовательности сообщений, не назначать
всем сообщениям канала одну дату. Извлекать отдельные события из TextUrl/entities
и текста, со ссылкой на реальный Telegram-пост и исходную Afisha-карточку.
Время, цена и описание могут отсутствовать; не заполнять их догадками. Уже прошедшие
сегодня сеансы отбирать по обычным правилам подборки.

## Будущие даты: усиленный web search

В дополнение к обычным LLM Web источникам выполнить отдельный пакет hosted
web search по событиям Afisha.rs за всю будущую часть периода. Один общий запрос
не заменяет этот пакет. Использовать сочетания:

- `site:afisha.rs` + Белград/Belgrade/Beograd + конкретные даты, месяц и год;
- варианты дат на русском, английском и сербском; не ограничиваться `/ru`,
  английская версия может находиться лучше;
- тематические запросы по нужным группам: концерты, театр/стендап, лекции,
  квизы/общение, фестивали и доступные групповые активности;
- найденные категории и площадки Afisha, затем конкретные исполнители и названия
  найденных событий для уточнения деталей и поиска первичного анонса/билетов.

Для двух недель пройти обе части периода; для дальнего горизонта разбивать по
месяцам и существенным категориям. Учитывать события, начавшиеся раньше, но
продолжающиеся в требуемые дни: запрос только по точной дате их пропускает.
Повторяющиеся результаты после уточнения запросов — повод зафиксировать предел
покрытия и перейти к другим источникам, а не бесконечно повторять поиск.

Считать отдельно найденные карточки и краткие упоминания в списках площадок.
Для каждой находки проверять год, дату/диапазон и город; время/цену/язык — только
при явном подтверждении. Если прямое чтение Afisha возвращает пустой текст/403,
проверять организатора, площадку, билетный сервис или доступный Radar reader.
Содержимое поискового ответа сохранять с provenance как индексированные данные;
оно не доказывает свежую доступность оригинала, отсутствие отмены или билетов.
Короткое упоминание без достоверных даты и места остаётся кандидатом на уточнение.
Недоступность источников не компенсировать выдуманными полями или событиями.

## Общая обработка и отчёт

До персонального LLM-анализа применять обычный скрытый фильтр. Сохранять прежние
правила рекомендаций: исключения разделов Afisha, география, язык, профиль,
сохранённые реакции и scoring. Резервный способ получения не расширяет критерии.
Дедуплицировать общий sync, Telegram, web и Radar reader: один и тот же числовой ID
в суффиксах Afisha `-ru`, `-en`, `-sr` — одна identity события; учитывать конкретный
сеанс/даты. Использовать существующую карточку при совпадении. Для новых импортов
заполнять `knownIds.afisha_rs`, когда ID подтверждён, и хранить реальные URL.

Сохранять реальные snapshots/checkpoints и поисковые receipts/query-summary по
основному workflow. В notes снимка и финальном результате указать: Afisha sync
получил 403, какие даты покрывались Telegram и web, где остались неизвестные детали
или неполное чтение. Не превращать fallback в успешный sync и не заявлять полное
покрытие по поисковой выдаче. После восстановления прямого доступа применять
обычный sync; Telegram и web остаются общими источниками подборки.
