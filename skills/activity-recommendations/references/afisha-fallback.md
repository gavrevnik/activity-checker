# Afisha.rs: облачный MCP → локальный sync при 403 → резервный сбор

Применять при формировании рекомендаций или дайджеста для покрываемой Afisha.rs
географии Белграда. Это порядок работы модели, а не автоматическое переключение
внутри сервиса. Обычный технический sync сам не запускает MCP, Telegram или LLM Web.
Не менять provider config, credentials, расписания или Knowledge.

## 1. Сначала облачный Personal Radar MCP

Локальный sync Afisha заранее не запускать, даже если сегодня нет успешного
`sync_runs`: общее правило обновления агрегаторов здесь не применяется. Не вызывать
общий `/api/sync`, который запустит Afisha до облачного этапа; остальные источники
обновлять отдельно. Облачный MCP не заменяется локальным одноимённым обработчиком.

Использовать `afisha_read_events_batch` с четырьмя `sections[].section`:
`concerts`, `standup`, `festivals`, `cinema`. Это принятый целевой охват Afisha;
остальные разделы специально не добирать и не считать их отсутствие ошибкой.
Обычный поиск других источников под профиль продолжается независимо от этого охвата.
Передать `startDate`/`endDate` за объединённый период выбранных вкладок, сохранить
новый UUID `requestId` до вызова. Для площадки поддерживается `sections[].venueUrl`.

Дочитать автоматическую пагинацию и сохранённые результаты через
`radar_get_batch_result` с `batchId`, полученным в ответе. `hasUnread` означает
невыданные результаты, `hasMore` — незавершённый обход: читать страницы результата
и продолжать provider work через `resume=true` с тем же batch/request ID до
завершения или явной ошибки. Физический бюджет страниц не равен концу каталога;
пустая отфильтрованная страница не отменяет continuation. После потери ответа
сначала восстановить тот же batch, не создавать новый запрос на тот же сбор.

Если чтение завершено без ошибок, использовать полученные карточки; локальный
sync не нужен. Корректный пустой результат — успех, а не повод запускать sync.
Успех ограничен четырьмя разделами и реально проверенным диапазоном. Данные
`cinema` допустимы по актуальному профилю: исключения «Кино»/«Дети» локального
адаптера не переносить автоматически на облачное чтение.

Проверять ошибки отдельных разделов и continuation, а не только HTTP 200 внешнего
MCP-вызова. Только подтверждённый HTTP 403 от Afisha.rs, включая Cloudflare challenge,
включает локальный этап ниже; OAuth/авторизационный 403 самого MCP не является
403 Afisha. Если tool отсутствует, авторизация недоступна или произошла другая
ошибка, локальный sync не запускать: сохранить валидные данные и перейти к
резервному сбору. Незавершённое чтение отмечать как partial, не выдавать за полный успех.

## 2. Только после облачного Afisha HTTP 403: локальный sync

Выполнить одну штатную попытку sync Afisha через локальный aggregator tool/API,
соблюдая существующие plan/confirmation, блокировку SyncService и cooldown.
Проверить фактическую ошибку облачного этапа; 403 другого источника не включает
эту ветку. Для всего прохода не повторять заведомо заблокированный запрос в цикле
и не запускать новый sync для каждой площадки, раздела или вкладки.

Локальный адаптер читает все страницы общего `/ru` feed, затем фильтрует даты
по нормализованным событиям; не обещать удалённый date filter. Он исключает «Дети»
и «Кино», поэтому не считать его полным покрытием всех четырёх облачных разделов.
Из результата использовать карточки целевых разделов и сохранить ограничения;
provider config и остальные карточки локальной базы не менять.

При успешном sync использовать его данные вместе с валидными облачными карточками,
не перечитывая уже покрытые разделы. Если sync завершился ошибкой, заблокирован
или вернул partial, не прерывать подборку: использовать всё достоверно полученное
и перейти к резервному сбору для непокрытых разделов/дат. Если локальный запуск
невозможен, явно указать причину и также продолжить резервный сбор. Не импортировать
непроверенные промежуточные страницы неуспешного sync в обход штатного адаптера.

## 3. Резервный сбор для оставшегося покрытия

Дальнейшие Telegram/web шаги нужны для недоступных или неполностью прочитанных
целевых разделов и дат. При полном успехе облака специальный Afisha fallback
не нужен; общий обход Telegram, площадок и hosted web search остаётся обязательным.

## Разделить период

Определить `today` по текущим часам в `Europe/Belgrade` и сравнивать календарные
даты, не UTC-день. Для непокрытой части объединённого периода запрошенных вкладок:

- если период включает today, покрыть текущий день официальным `@afishars`;
- будущую часть от `max(начало периода, завтра)` до конца периода покрыть
  усиленным web search с фокусом на Afisha.rs;
- для запроса только будущих дат не добавлять сегодня и не выполнять отдельное
  чтение канала ради сегодняшней подборки. Обычный полный обход Telegram остаётся.

Сохранённые карточки Afisha и ранее прочитанные raw-анонсы остаются дополнительным
материалом с исходной датой проверки. Не объявлять их свежей синхронизацией.
Другие агрегаторы, включая Tickets.rs и AllEvents, и общий поиск продолжаются.
Для географий вне покрытия Afisha.rs использовать их scoped источники.

## Сегодня: официальный Telegram

Разрешить Knowledge source `telegram-afishars`: `https://t.me/afishars`, подтверждённый
numeric channel ID `1886741665`. Сверить актуальные enabled/access и локальные
исключения. `@afisha_rs` с подчёркиванием — другой источник и не заменяет этот канал.
Отключение/недоступность раскрыть как пробел, не менять подписки и Knowledge.

Использовать общий monitoring batch и сохранённые raw-снимки; не перечитывать уже
полученные сообщения без необходимости. Проверить публикации за вчера и сегодня:
сегодняшний дайджест мог выйти вчера под заголовком «Планы на завтра». При старом
checkpoint дочитать новые сообщения и восстановить нужное окно из raw; если его
нет или требуется проверить правки, перечитать это окно с обычными фильтрами и
пагинацией. Не сужать глобальное чтение всех каналов до этих двух дней.

Разбирать все продолжения подборок, а не только первый пост. Дату события брать
из заголовка/анонса; дату публикации не подставлять вместо неё. Связывать части
подборки по подтверждённому заголовку и последовательности сообщений, не назначать
всем сообщениям канала одну дату. Извлекать отдельные события из TextUrl/entities
и текста, со ссылкой на реальный Telegram-пост и исходную Afisha-карточку.
Время, цена и описание могут отсутствовать; не заполнять их догадками. Уже прошедшие
сегодня сеансы отбирать по обычным правилам подборки.

## Будущие даты: усиленный web search

В дополнение к обычным LLM Web источникам выполнить отдельный пакет hosted
web search по событиям Afisha.rs за всю будущую часть периода. Один общий запрос
не заменяет этот пакет. Использовать сочетания:

- `site:afisha.rs` + Белград/Belgrade/Beograd + конкретные даты, месяц и год;
- варианты дат на русском, английском и сербском; не ограничиваться `/ru`,
  английская версия может находиться лучше;
- тематические запросы по недостающим целевым разделам: концерты, стендап,
  фестивали и кино; другие темы остаются частью обычного поиска под профиль;
- найденные категории и площадки Afisha, затем конкретные исполнители и названия
  найденных событий для уточнения деталей и поиска первичного анонса/билетов.

Для двух недель пройти обе части периода; для дальнего горизонта разбивать по
месяцам и существенным категориям. Учитывать события, начавшиеся раньше, но
продолжающиеся в требуемые дни: запрос только по точной дате их пропускает.
Повторяющиеся результаты после уточнения запросов — повод зафиксировать предел
покрытия и перейти к другим источникам, а не бесконечно повторять поиск.

Считать отдельно найденные карточки и краткие упоминания в списках площадок.
Для каждой находки проверять год, дату/диапазон и город; время/цену/язык — только
при явном подтверждении. Если прямое чтение Afisha возвращает пустой текст/403,
проверять организатора, площадку или билетный сервис. Не возвращаться циклически
к уже заблокированным облачному/локальному этапам.
Содержимое поискового ответа сохранять с provenance как индексированные данные;
оно не доказывает свежую доступность оригинала, отсутствие отмены или билетов.
Короткое упоминание без достоверных даты и места остаётся кандидатом на уточнение.
Недоступность источников не компенсировать выдуманными полями или событиями.

## Общая обработка и отчёт

До персонального LLM-анализа применять обычный скрытый фильтр. Сохранять прежние
правила рекомендаций: принятый охват Afisha, география, язык, профиль,
сохранённые реакции и scoring. Резервный способ получения не расширяет критерии.
Дедуплицировать общий sync, Telegram, web и Radar reader: один и тот же числовой ID
в суффиксах Afisha `-ru`, `-en`, `-sr` — одна identity события; учитывать конкретный
сеанс/даты. Использовать существующую карточку при совпадении. Для новых импортов
заполнять `knownIds.afisha_rs`, когда ID подтверждён, и хранить реальные URL.

Сохранять реальные snapshots/checkpoints и поисковые receipts/query-summary по
основному workflow. Облачное чтение и импорт его карточек не создают успешный
локальный sync: не подменять `sync_runs`, `lastSyncAt` или provider run receipts.
В следующие обновления также начинать с облачного этапа; доступность локального
источника сама по себе не возвращает прежний порядок.

После обновления обязательно написать в чате и сохранить в `notes` статус
каждого этапа: **успех / частично / заблокирован / ошибка / не запускался**,
краткую причину и реально покрытые разделы/даты; для прочитанных этапов — число
валидных уникальных карточек. У пропущенного шага указывать причину, например
«локальный sync не запускался: облачный MCP успешен» или «в облаке не было Afisha 403».
Разделять специальный Afisha fallback и обычный web search, который выполняется
независимо от него. Указать, какие данные использованы и где остались пробелы;
поисковую выдачу не объявлять полным свежим каталогом.

Пример формы отчёта (значения заменять фактическими):

- Afisha, облачный MCP: заблокирован, HTTP 403; часть разделов прочитана.
- Afisha, локальный sync: ошибка; доступные облачные карточки сохранены для отбора.
- Afisha, резервный сбор: выполнен через `@afishars` и web search; покрытие частичное.
