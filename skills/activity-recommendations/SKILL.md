# Рекомендации активностей

Собери и сохрани персональные рекомендации на отдельной странице Activity Checker. По
умолчанию обновить три вкладки: **остаток текущей календарной недели**, **следующую
календарную неделю (понедельник–воскресенье)** и **предстоящие концерты, выступления и
фестивали до конца 2026 года**. Если пользователь явно ограничил запрос одной вкладкой
(«только»), обновить только её.

Это отдельные снимки; не создавать дополнительно AI-дайджест без запроса. Создание или
редактирование скилла не запускает сбор.

Вызов разрешает обычную бесплатную синхронизацию подключённых агрегаторов,
чтение Telegram, web search, штатные импорт/архивацию/AI-review и сохранение
рекомендаций. Не менять подписки, исключения источников, промпты, личные реакции
или Knowledge. Для платных провайдеров и провайдеров с ограниченной квотой нужен бюджет
текущего прохода по правилам проекта. Не заменяй ими бесплатные источники автоматически.

Работай из актуальной рабочей копии Activity Checker. Прочитай её `AGENTS.md`, [API и
workflow рекомендаций](references/workflow.md), [поиск концертов по
Knowledge-площадкам](references/concert-search.md), репозиторные [workflow
digest](../digest/references/workflow.md) и [ai-events-review](../ai-events-review/SKILL.md)
с его API-reference. Не выполняй вложенный digest целиком.

Используй его сбор, память, удаление дублей и оценку один раз, затем сохраняй результат
через recommendations API.

Рабочий локальный путь без облачных подключений описан в
[start/references/local-tools.md](../start/references/local-tools.md). Если нужные tools не
зарегистрированы в клиенте, вызывать те же обработчики через `scripts/local-tool.ts`; не
останавливаться на отсутствии глобального MCP.

Перед первым сбором выполнить `npm run start:verify`, при необходимости подготовить
метаданные выбранных Telegram-источников через `/api/recommendations/prepare-sources`.

Все личные вкусы и языки брать только из актуального `/api/profile`, включая
`additionalPreferences`, `recommendationPrompts`, `automaticFilters` и
`excludedTelegramChannels`. Условия образца не являются правилами сервиса. Для Afisha.rs
сначала использовать облачный Personal Radar MCP по сценарию ниже; его отсутствие не
блокирует подборку.

Остальные локальные инструменты, чтение Knowledge и Telegram не требуют облачного Personal
Radar, GitHub runtime token или Agent Stack.

## Периоды и критерии

Получить `/api/recommendations?scopeId=…&kind=week`, `kind=next-week` и/или
`kind=concerts-2026` для выбранной географии. Использовать возвращённые `period`,
`timeZone`, `settings.prompts` и revision. Текущая неделя — с сегодняшнего дня по
воскресенье, **не следующие семь дней**.

Следующая — полный понедельник–воскресенье после текущей недели, в том числе при переходе
месяца/года. При обновлении текущей недели можно и по умолчанию нужно заодно заполнить
следующую из того же потока источников: один раз читать Telegram, агрегаторы и web за
объединённый диапазон, дедуплицировать и оценивать кандидатов, затем разложить их по двум
периодам и сохранить отдельные снимки `week` и `next-week`.

Не повторять одинаковые сетевые вызовы ради второй вкладки. Если данные уже покрывают обе
недели, использовать сохранённые raw-анонсы; дополнять только недостающий диапазон. Явное
«только текущая неделя» ограничивает публикацию этой вкладкой.

Город берётся из `scopeId`, его country/city/timezone, а не из упоминаний Белграда в общем
профиле или ранее сохранённых промптах. Вкус и четыре группы общие; предпочтительные языки и
допустимую программу читать из текущего профиля. Для Кишинёва не переносить сербские
источники и площадки: брать scoped `/recommendations/sources`, сайты/каналы нужного города и
общестрановые источники Молдовы с проверкой места события.

Румынское название или язык сайта не доказывают язык программы; для разговорных форматов на
непонятном языке учитывать барьер, food/outdoor не понижать за географию. Стартовый ресерч
кандидатов — `docs/research/chisinau-sources-2026-10-16.md`; реализация источников и
ограничения покрытия описаны в `docs/moldova-connectors.md`.

Для годовой вкладки просматривать всю доступную выгрузку до 31 декабря 2026, оставляя только
события с предстоящей датой начала. После 2026 года вкладка остаётся исторически
именованной: не подменять её новым годом и не сохранять прошедшие события как предстоящие.

Скрытые рекомендации — отдельный пользовательский список, общий для всех вкладок в
географии. До анализа релевантности каждого пакета исключи их программно через
`/api/recommendations/filter-candidates` или репозиторный helper из
[workflow](references/workflow.md#скрытые-события-до-llm-анализа). Не печатать исходные
отфильтрованные карточки в контекст модели и не выставлять им AI-score.

По-прежнему читай все каналы и полностью сохраняй snapshots/checkpoints; исключение
происходит после извлечения минимальных полей даты/названия/источника, до персонального
анализа. Не восстанавливать скрытое при обычном обновлении и не превращать его в dislike.

Текущие редактируемые промпты — единый источник критериев для каждой группы. Читать их
заново перед финальным отбором, вместе с актуальным профилем, музыкальными предпочтениями,
feedback-summary и query-summary. Промпты — часть профиля и возвращаются также совместимым
`/recommendations/settings`.

Явный запрос пользователя важнее образца; при противоречии актуальных условий уточнить
только спорный пункт. В sport/walks/social/concerts распределять по основной программе, без
заданных заранее личных приоритетов. Даты, реальность, прямые ссылки, дедупликация и защита
личных состояний обязательны при любом профиле.

### Персональные правила отбора

Читать дополнительные условия профиля целиком. Если пользователь задал широкое
включение определённой языковой/тематической программы, применять его с честной
оценкой, а не как обязательное правило для всех людей. Если такого условия нет,
не добавлять его из памяти, старого чата или профиля-образца. Социальные цели,
игры, языки, музыка и отношение к локальной сцене определяются только профилем.

## Сбор: все каналы, агрегаторы и веб-источники

1. Обновить pending feedback/query memory по digest и ai-mcp-discovery. Проверить bootstrap,
   настройки Telegram и успешность **каждого** нужного агрегатора. Afisha.rs исключить из
   предварительного локального sync и обрабатывать только по шагу 2, в том числе при
   переиспользовании digest workflow.

   Для Белграда обновить AllEvents Belgrade штатным API, если нет сегодняшнего успеха либо
   прежний диапазон не покрывает запрос. AllEvents: сначала sync-plan, затем sync с теми же
   фильтрами, `previewId`, `confirmed=true`; вызов skill уже разрешает этот бесплатный
   запуск. Источники синхронизировать последовательно.

   Для Кишинёва использовать `source-fest-md`, `source-iticket-md`, `source-afisha-mira`,
   `source-afisha-md` и `source-allevents-chisinau`. У AllEvents тот же transport с
   `city=chisinau`; не менять сербский source. Afisha.md вызывать отдельно (manualSyncOnly)
   через штатный sync с доступным anonymous renderer; нет renderer — обозначить пробел.

   Общий диапазон сбора охватывает обе недели, затем разложить результат по снимкам.
   Fest/iTicket/Афиша мира/Afisha.md имеют возобновляемый обход: читать coverage, повторять
   sync с теми же датами до конца очереди/discovery; не менять диапазон между продолжениями.

   Физический лимит деталей не является концом каталога. iTicket читает публичный Livewire
   loadMore и сохраняет отдельные подтверждённые сеансы; нулевые placeholders цены не
   означают бесплатность. Afisha.md перечисляет страницы через публичный sitemap, renderer
   подтверждает список и помогает деталям. `inLanguage=ru` и русский интерфейс не доказывают
   язык программы.

   Afisha Mira: REST date — публикация, время основного блока трактуется в Europe/Chisinau.
   Также отдельно синхронизировать `source-sporter-md`, `source-moldova-travel`,
   `source-frc-chisinau` (manualSyncOnly). unresolved/warnings не считать подтверждёнными
   событиями; неизвестную пагинацию дополнить web. У Moldova Travel не подставлять текущий
   год, у FRC не создавать встречи из общего расписания.

   Locals/Artcor/ America House/Tekwill/TopAlpine проверять целевым web search из scoped
   Knowledge. Для Кишинёва также искать в #diez и E-Tineret (`source-diez-md`,
   `source-e-tineret-md`), применяя языки и интересы текущего профиля, ограничения возраста
   и реальный допуск.

   Языки программы сверять с текущим профилем и анонсом, возраст не угадывать; KEDEM и
   InterNations (`enabled=false`, reference) остаются вне активного обхода.

2. Afisha.rs: сначала облачный `afisha_read_events_batch` Personal Radar MCP, разделы
   `concerts`, `standup`, `festivals`, `cinema`; это принятый целевой охват, остальные
   разделы Afisha специально добирать не требуется. За один логический сбор покрыть
   объединённый период вкладок и дочитать все страницы/результаты. При успехе использовать
   карточки без локального sync.

   Только подтверждённый HTTP 403 от Afisha в облачном reader включает одну попытку штатного
   локального sync. При его неудаче сохранить всё достоверно полученное и продолжить
   Telegram/web. Другая ошибка или отсутствие облачного tool ведёт сразу к резервному сбору,
   без локального sync.

   Полный порядок, partial и отчёт этапов — в [Afisha
   workflow](references/afisha-fallback.md).

3. **Полный список Telegram брать из Personal Radar Knowledge**, а не только из локального
   списка Community и не из прошлого чата. Разрешить коллекцию
   `activity-telegram-channel-monitoring`: все enabled public channels с domains=activities
   и role=activity_monitoring.

   Дополнительно из `activity-telegram-monitoring` брать публичные группы с явно указанным
   `access.method=personal_radar_mcp`, `access.tool=telegram_read_messages`; локальный
   `telegram_monitoring_posts` поддерживает публичные группы с rich DTO. Не требовать
   одноимённого облачного tool.

   Для Кишинёва проверять: CC_151 — подтверждённый язык программы и соответствие аудитории
   текущему профилю; FRIENDS — конкретные офлайн-встречи; VoleiNet — уровень, переносы и
   отмены игр. Прочитать описания/metadata источников. Точный способ перечисления — в
   reference.

   Сопоставить локальные исключения; явно сообщить расхождения, не включать отключённые
   источники.

4. Прочитать **каждый** допустимый канал списка, независимо от первых найденных
   хороших событий. Передавать usernames/URLs напрямую, если канала нет в локальной
   Community. Разбить на последовательные batches до 20, сохранять реальные
   snapshots/checkpoints по digest. Без истории — последние 30 дней публикаций;
   с историей — новые посты плюс сохранённые raw-анонсы всех дат. `truncated=true`
   требует пагинации. Дата поста не является датой мероприятия.

5. Для дальнего горизонта дополнительно использовать все уже сохранённые анонсы, полную
   выгрузку агрегаторов и scoped Telegram search по исполнителям/месяцам в подходящих
   каналах. Если анонс старше первого 30-дневного окна, дочитать нужный старый диапазон с
   пагинацией. Не ограничивать концерты недельной выгрузкой.

   FloodWait/auth/unknown dispatch не обходить новым аккаунтом/request ID; продолжить
   доступные ветки, сохранить незавершённую границу и раскрыть пробел.

6. Для музыкальной/концертной программы обязательно выполнить [общий поиск по
   Knowledge-площадкам](references/concert-search.md): все P1, затем P2 под профиль,
   P3/сезонные, стендап и организаторов.

   Каталог получать из `/recommendations/sources` (`venues`) либо разрешённых
   Knowledge-коллекций; при наличии `venue.afishaVenueUrl` использовать облачный reader с
   `venueUrl` по тому же [Afisha workflow](references/afisha-fallback.md), переиспользуя уже
   полученные карточки и статус блокировки; дополнить hosted Web Search. Не копировать
   список в skill.

   Годовой поиск разбивать по оставшимся месяцам; несколько концертов агрегатора не
   доказывают полноту. Язык конкретного шоу проверять по языкам текущего профиля; трибьют не
   равен оригинальному артисту.

7. Использовать собственный hosted web search. Проверить Meetup.com, Eventbrite, Belgrade
   Beat и прочие актуальные sources с `webSearchLlm` из bootstrap, сайты организаторов,
   площадок и артистов. Для спорта/природы/общения искать варианты на языках профиля и
   местных источников с географией и явными датами.

   Для годовой вкладки — также фестивали еды/вина/музыки и другие профильные фестивали, по
   месяцам, именам интересных артистов и известным комикам. Проверять оригинальные страницы,
   год, время, место, регистрацию, отмены/переносы и подтверждённый язык программы.

Для каждого канала и источника отмечай полноту чтения: прочитан полностью / частично / недоступен /
исключён. Нельзя объявлять Telegram просмотренным полностью, пока остаётся хотя бы
один непрочитанный допустимый канал или pending cursor. Нельзя выдумывать события
или время, чтобы заполнить пустые дни календаря.

## Отбор и сохранение

После сбора и исключения скрытых событий перечитай оставшиеся карточки, профиль
и промпты. Убери подтверждённые дубли
между источниками по программе, месту, сеансу и первичным ссылкам. Сохранить
проверенные новые события и оценки содержательно рассмотренных кандидатов
штатными путями digest; не менять личные состояния, кроме предусмотренного
нейтрального skip подтверждённых дублей. Учитывать dislikes, skip и архив.

Отбирать сильные попадания по группам, без обязательной квоты на каждый день. События обеих
недель могут также присутствовать в годовой вкладке concerts; это два представления, не два
canonical Event.

Оценённые события, отклонённые из-за низкой релевантности/score или персональных критериев,
сохранять в `rejectedItems` того же снимка: полная карточка с `aiScore`, `group` и
`rejectionReason` (кратко, почему не прошла). Отсутствие оценки, дубль, неподтверждённая
дата и пользовательское скрытие не являются отказом по оценке: не включать их в этот список.

Не помещать одно событие одновременно в `items` и `rejectedItems`; оба списка относятся к
тому же scope/периоду, годовой — только concerts. Перед анализом и публикацией применять
фильтр скрытого к обоим спискам. Не вводить произвольный общий порог: отбор следует текущим
промптам и профилю.

Каждая карточка: точное название, описание **1–2 предложения**, `group`, `aiScore`,
проверенная дата/время, название источника, прямая ссылка на событие и ссылка на
источник/пост. Неизвестное время — дата без timestamp; не придумывать 12:00/20:00. Карточки
календаря распределяются только по дате начала и показываются один раз.

В интерфейсе каждому событию отведён условный час, даже если оно длится дольше; не подменять
этим реальный endAt в исходных данных или снимке. Совпадающие часовые слоты показываются
списком названий с подробной модалкой. Для интервала сохранить подтверждённое окончание;
повторяющиеся несмежные сеансы — отдельные карточки.

Существенные неизвестные сообщить в описании.

Перед публикацией повторить фильтр скрытого и прошедших событий по свежему серверному
периоду: пользователь мог скрыть карточку, а день мог смениться во время поиска. API и
календарь также исключают скрытое и предыдущие дни автоматически. Сохранить новый UUID через
`/api/recommendations` с актуальными `settingsRevision` и `expectedSnapshotId`.

При недоступном источнике сохранить доступную подборку только с явным предупреждением в
`notes`, перечислив пробелы и покрытие Telegram. Пустая подборка допустима при реально
выполненном поиске; полный технический сбой не считать успешным обновлением и не заменять им
старый снимок. При конфликте перечитать и пересмотреть; повтор неизвестного результата — тот
же UUID/payload.

Проверить сохранение GET-запросом. Повтор старого UUID не делает старый снимок текущим.
Снимки независимы от последующего архива исходных событий.

В чате кратко сообщи период, число сохранённых событий по группам и вкладкам, покрытие всех
Telegram-каналов и существенные ограничения. Отдельно перечислить статусы этапов Afisha:
облачный MCP, локальный sync, резервный Telegram/web — что прошло, заблокировано, выполнено
частично или не запускалось и почему. Те же факты сохранить в `notes`; успешный облачный
reader не считать локальным sync.

Ссылка на страницу: [Рекомендации Activity
Checker](http://activity-checker.localhost/#recommendations). Рекомендации доступны сразу на
главной странице, без основной ленты вкладок. Не создавать расписание без отдельного запроса
пользователя.
