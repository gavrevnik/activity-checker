# Repository instructions

When this checkout is inside `life-stack`, first read the shared [workspace instructions](../AGENTS.md) if they have not already been loaded. This file supplies project-specific overrides. If the shared file is absent in a standalone clone, continue with this file.

- Communicate with the user in Russian unless they request another language.
- Preserve unrelated changes and never publish, delete, or rewrite data without an explicit request.
- The canonical repository is https://github.com/gavrevnik/activity-checker.
- The default branch is `master`.
- The live SQLite database is `../data/activity-checker/activity.sqlite` in the standard `life-stack` layout. `ACTIVITY_DB` may override it.
- Never use the live database in tests. Tests must use in-memory or temporary SQLite databases.
- Keep provider secrets only in the ignored `.env.local`; never include them in source, fixtures, logs, or chat output.
- Update `README.md` when setup, storage, providers, or user-visible behavior changes.
- Before handing off code changes, run `npm test`, `npm run check`, and the relevant focused verification.
- For profile-guided MCP discovery/enrichment (including "using MCP TG find new channels about …") and user-requested LLM sync/filter/review of ordinary aggregators such as Tickets.rs, use `ai-mcp-discovery` at `skills/ai-mcp-discovery/SKILL.md`. Refresh shared preference feedback and keyword-query memory before planning and after completed search batches. For quota-limited/paid providers, show available total/used/remaining quota and obtain a per-run spending limit before live calls; a previous run's budget is not authorization. Do not activate this workflow for a purely technical sync without LLM selection.
- For a personal activity digest by dates or topic (week/weekend plans, concerts, professional meetups), use `skills/digest/SKILL.md`: refresh each due aggregator, archive past events, incrementally monitor enabled Telegram channels, research current LLM Web sources, deduplicate and persist reviewed event scores before returning recommendations. A digest request authorizes these routine updates/imports; paid-provider budgets remain separate. Creating/editing the skill does not execute a digest.
- For Telegram channel discovery, use `activity-checker-telegram-discovery`: batch up to 30 useful hypotheses, start with non-mutating channel-name search, deduplicate all stored/hidden/excluded communities, then inspect description/size → current pins without date bounds → recent posts, and optionally expand from relevant seeds with recommendations. Set `store=true` only when the user asks to enrich Activity Checker. Global full-text post search is disabled; scoped `telegram_search_channel_messages` is available in discovery and monitoring. For posts from known channels, use `activity-checker-telegram-monitoring`, batch at most 20 channels, prefer date/message-ID bounds, and keep the conservative sequential delay. Never authorize Stars spending; stop on FloodWait or an authorization requirement.
- When forum topics help discovery, list them with `telegram_group_topics`, announce the closest topic and why, then read a bounded `telegram_topic_posts` sample. Use verified linked-chat/posts-comments tools only to answer a concrete research question (community interaction, participation/logistics); no auto-join/import. Discussion replies are intentionally included without changing feed settings; channel/keyword/ad exclusions remain active. See `docs/TELEGRAM_DISCOVERY.md`.

- Для публичного веб-исследования и обычной синхронизации доступны tools `npm run research:mcp`: web search/read, aggregator status/history/plan/sync и archive. Использовать прежний SyncService; не менять source URLs или credentials через этот MCP. Если полезный шаг запроса/скилла недоступен из-за инструмента, права, ключа, сессии, бюджета, CAPTCHA или JavaScript, прямо сообщить об этом в текущем чате: какой шаг/источник пропущен, влияние на результат и какой доступ нужен. Продолжить доступную работу; не объявлять неполное покрытие полным.

- Google Places MCP: только Basic/IDs-only и Pro, общий защищённый лимит 100 HTTP-запросов в сутки Europe/Belgrade (ошибки тоже учитываются). Перед КАЖДЫМ новым запуском прочитать `google_places_status`, показать остаток и уточнить у пользователя максимум запросов; передать `maxRequests`, не переносить бюджет предыдущего запуска. Enterprise в MCP отсутствует. Для новых мест использовать discovery либо `newOnly=true`, исключать только существующие карточки ресторанов Activity Checker (классификация как во вкладке «Рестораны»). Google Takeout отложен владельцем: не использовать индекс списков, не запрашивать выгрузку и не считать её отсутствие препятствием. История discovery сама по себе не означает, что место уже знакомо.

- JavaScript-чтение публичных страниц: `activity_web_status`, `activity_web_read(render="browser"/"auto")`; отдельный анонимный browser worker без owner profile/cookies/login/forms/arbitrary scripts. Для рейтинга ресторана нужны совпавшие название/адрес и явное число на странице, URL/дата проверки; minRating API и сниппет не подтверждают точный рейтинг/число отзывов. Если Google отдаёт limited view или не показывает reviewCount, прямо указать это отдельно. При поиске игнорировать нерелевантную выдачу, CAPTCHA не обходить.

- В Claw общий веб-поиск выполнять штатным hosted `web_search` Codex (live) через текущий OAuth-транспорт. `activity_web_search` — запасной HTML-поиск; `activity_web_read(render="browser")` — чтение динамической страницы по известной URL. Native search и чтение страницы — разные возможности; искать дополнительный API key для штатного hosted search не требуется.

- Для погоды использовать `activity_weather`; проверять координаты, timeZone и даты. Числа возвращаются с единицами и временем получения; прогноз не равен гарантии. Указывать Open-Meteo как источник.

## Общие коннекторы и Knowledge

- Provider API/transport implementations находятся в [Personal Radar connectors](../personal-radar/connectors/README.md); SQLite, domain filters/dedupe/AI/UI и прикладные MCP остаются здесь. Сохранять обязательные quota adapters; тестировать внешние операции mocks на фактическом общем модуле.
- `personal-radar/knowledge` — канонический каталог долгосрочных знаний. Текущие SQLite-профили, источники/интересы и реакции сохраняются без автоматической миграции. Следовать [границам владения](../personal-radar/docs/storage-boundaries.md); использовать [Catalog Sync](../personal-radar/docs/catalog-sync.md): mapping/cache, атомарный outbox только однозначных canonical fields, ручной flush; discovery/new/conflict — pending review, без автоматического GitHub publish.
- Discovery возвращает source-кандидатов: name/URL/platform/external IDs/description/provenance/evidence/relevance. Review/deduplication по стабильной identity предшествуют потенциальному переносу подтверждённых источников в Knowledge отдельным запросом. Разрешённые локальные импорты продолжают использовать прежние tools/flags/budgets; discovery/digest не разрешают запись Knowledge.

- Telegram Connector: portable API находится в `@personal-radar/connectors/telegram`, Node/Telethon adapter — `telegram/local`. Старые MCP schemas/caps сохранены; durable `telegram_batch_read` принимает до 50 sources на logical UUID request. Runtime journal/gates — в existing activity.sqlite (migration 030), без automatic domain ingestion/Knowledge migration. Не продвигать watermark для partial/unknown; не replay unknown/terminal failures без explicit retry decision; соблюдать persisted FloodWait между request IDs. См. [архитектуру и границы](../personal-radar/docs/telegram-connector.md).

- Catalog Sync: before schema/pull/review/flush changes create WAL-aware verified SQLite backup; tests use synthetic temporary DB/YAML. Preserve Radar IDs, local overrides, notes/CRM/workflow/consumption state. Never approve pending review heuristically; source interest ≠ enabled/favorite, AI ≠ personal liked. GET /api/catalog is local/cached; no automatic startup GitHub sync.
