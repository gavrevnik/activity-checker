# Activity Checker

Локальный сервис для сбора, нормализации и просмотра событий, ресторанов, сообществ и мест. Доступные географии — Белград и Кишинёв. Приложение рассчитано на одного пользователя: без аккаунтов, фонового обхода сайтов и встроенного LLM. Модель взаимодействует с сервисом снаружи — через локальный API и MCP-инструменты.

## Первый запуск для нового пользователя

Клонируйте `activity-checker` и выданный `personal-radar` в одну папку рядом.
Откройте Activity Checker в агенте и вызовите **$start**: репозиторий содержит
обнаруживаемые `.agents/skills/` и [полную инструкцию](skills/start/SKILL.md).
Если клиент не обнаруживает skills автоматически: «Прочитай skills/start/SKILL.md
и выполни первый запуск». Нужны агент с локальными командами, Node 24+ и интернет
для установки. Life Hub, Agent Stack, глобальные MCP, облачный Site и ключ OpenAI
для самого сервиса не требуются.

`start` коротко проверяет окружение/ключи, предлагает инструкции для выбранных
подключений, создаёт личную SQLite без demo-событий, затем уточняет город, языки
и интересы. [Профиль владельца](examples/recommendation-profile.json) — только
образец. До первой подборки агент обязательно предложит оставить, отключить или
выборочно изменить его условия, особенно приоритет русского языка. Для
молдавского/румынского языка задаются собственные условия; национальность не
определяет язык программы. База, ключи, реакции и сессия у каждого свои.

Ручные шаги: `node scripts/start-check.mjs`, `npm ci`,
`npm run start:setup -- --init`, `npm run browser:setup`, `npm run dev`.
После настройки профиля — `npm run start:setup -- --prepare-sources --scope chisinau`
(или `belgrade`) для локального mapping Telegram без чтения сообщений.
`npm run start:verify` проверяет схемы локальных tools, Chromium и при заданных
личных ключах — статус Telegram. Отсутствие Telegram не мешает публичному вебу.
[Локальные вызовы без MCP-конфигурации](skills/start/references/local-tools.md),
[доступы и личный вход](skills/start/references/connections.md).

Для Telegram нужны uv, Python 3.12, личные `api_id/api_hash` и интерактивный вход;
`npm run telegram:setup` устанавливает окружение, `npm run telegram:auth` выполняется
пользователем в терминале. Bot token не подходит. Apify/Ticketmaster необязательны.
Ключи можно внести в локальный файл с правами 0600 и импортировать
`npm run start:setup -- --import-keys /путь/keys.env`: файл разбирается как данные,
без shell source/eval. Значения не выводятся. После импорта временный файл удалить.

Повторяемая проверка чистого двухрепозиторного сценария:
`node scripts/check-onboarding-clean.mjs`. Она создаёт отдельный HOME и копии
исходников, устанавливает собственные Python/Chromium, собирает и запускает
сервис, затем проверяет профиль, локальный CLI, review, публикацию и календарь.
Провайдеры в сквозном тесте заменены fixtures; личные credentials не используются.
Путь к отчёту и временному окружению печатается в конце.

## Текущий веб-интерфейс

Главная страница сразу открывает рекомендации. Верхняя навигация и разделы
«Активности», «Источники», отдельная страница профиля временно скрыты; код и API
сохранены. Старое значение вкладки в localStorage не уводит с главной страницы.
«Запрос для модели» и «Мой профиль» оформлены одинаковыми подписанными кнопками.
В «Мой профиль» доступны личные предпочтения, поисковые критерии и список источников.
Кнопка ручного перечитывания убрана; сохранённые данные обновляются при возврате
в окно и каждые 30 секунд. Запуск поиска по-прежнему выполняет внешняя модель.

Рядом со «Скрытое (N)» находится «Не прошедшее фильтрацию (N)»: список оценённых
отказов выбранного периода, разделённый по дням, с обычными карточками, оценкой
и причиной. Он заполняется моделью в `rejectedItems` при следующем обновлении;
старые снимки не содержат историю отказов. Скрытые пользователем, истёкшие события
и дубли не отображаются как score-отказы. Фильтры календаря на этот список не влияют.

Далее описаны также сохранённые внутренние разделы/API, временно недоступные из
основной навигации. Для нового пользователя достаточно рекомендаций и `start`.

## Общие библиотеки и владение данными

Повторно используемые provider-клиенты находятся в соседнем `personal-radar/connectors/`; нужен checkout Personal Radar в стандартном Life Stack layout. [Установка и структура пакетов](../personal-radar/connectors/README.md), [inventory переносов](../personal-radar/docs/connector-inventory.md), [Knowledge/SQLite и future migration](../personal-radar/docs/storage-boundaries.md).

npm использует `file:../personal-radar/connectors/connectors-ts` и именованные импорты `@personal-radar/connectors/...`. Обычные install/dev/start/build/check/test и MCP-команды автоматически собирают библиотеку; при первом setup устанавливаются её lockfile-зависимости. Ручные symlink не нужны.

SQLite-файлы, текущие карточки/профили/оценки и API/MCP/UI контракты сохранены. Долгосрочные отобранные sources/owners/items/preferences принадлежат Personal Radar Knowledge; существующие локальные данные пока не мигрируют. Discovery сохраняет source-кандидатов с identity/provenance/relevance и явным review; подтверждённые источники предназначены для будущего отдельного переноса в Knowledge. Ручной versioned catalog sync и outbox для явно определённых канонических полей описаны в [Catalog Sync](../personal-radar/docs/catalog-sync.md); новые кандидаты требуют утверждённого manifest.

## Быстрое погружение

### Из чего состоит сервис

| Блок                    | За что отвечает                                                                                                                               |
| ----------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| **Активности**          | Основная выдача с отдельными вкладками «События», «Рестораны», «Сообщества» и «Места», поиском, фасетами, датами и сортировкой.               |
| **Правила фильтрации**  | Детерминированно скрывают нерелевантные карточки после нормализации. Исходные записи не удаляются, а счётчик показывает объём скрытых данных. |
| **Источники**           | Каталог подключений, их состояние и ручной запуск API-агрегаторов. Источники сгруппированы по способу работы: API, MCP, LLM Web и другие.     |
| **Карточка активности** | Показывает canonical-запись, ссылки на оригиналы, raw/provenance, заметку, связи и доступные действия редактирования или объединения.         |
| **Мой профиль**         | Кнопка на главной: предпочтения и критерии, которые учитываются при следующем обновлении моделью.                                       |
| **SQLite и pipeline**   | Сохраняют raw-ответы, нормализованные сущности, связи с источниками, историю синхронизаций, правила, квоты и профиль.                         |
| **MCP-инструменты**     | Дают модели управляемый поиск по Telegram, Apify, Foursquare и Google Places с явными лимитами и отдельным разрешением на запись.             |

### Источники истины

- Рабочие данные находятся во внешней SQLite-базе `../data/activity-checker/activity.sqlite`, а не в Git.
- Секреты находятся только в игнорируемом `.env.local`; `.env.example` содержит лишь имена переменных и безопасные значения по умолчанию.
- Схема данных развивается последовательными SQL-миграциями из `migrations/`.
- Каталог и возможности провайдеров задаются кодом в `server/providers/`; пользовательские настройки и состояние синхронизаций хранятся в SQLite.
- Интерфейс не является отдельным хранилищем: он читает и изменяет данные через локальный HTTP API.

### Обычный рабочий сценарий

1. Запустить сервис через Life Hub или `npm run dev`.
2. В **Источниках** запустить один API-агрегатор либо весь блок агрегаторов. Платные и исследовательские MCP-поиски инициирует модель, а не интерфейс.
3. Проверить новые карточки в **Активностях**, используя географию, тип, источник, тег, дату и локальный час начала.
4. При необходимости изменить **Правила фильтрации**: карточки пересчитаются без повторного импорта.
5. Периодически нажимать **Архивировать прошлые события**, чтобы переносить завершившиеся события из рабочей таблицы в архив.

## Запуск

Нужен **Node.js 24+**. Проект создан в этой директории, без вложенной копии и без инициализации Git.

```sh
npm ci
npm run dev
```

Откройте **http://127.0.0.1:4318** — Life Hub и Caddy для работы не нужны.
На macOS после первоначального setup можно запускать сервис двойным кликом по
**Activity Checker.app** в корне репозитория. Лаунчер запускает сервис в фоне;
если `http://activity-checker.localhost/api/health` через локальный Caddy подтверждает
Activity Checker, открывает красивый адрес, иначе автоматически открывает
`http://127.0.0.1:4318/`. Проверка Caddy занимает не более двух секунд и выполняется
также при повторном запуске уже работающего сервиса. Лаунчер использует стандартный
порт 4318; для другого `PORT` запускайте сервис из терминала и открывайте свой адрес.

Один процесс обслуживает API и React. Изменения фронтенда обновляются через Vite;
после изменения backend нужен перезапуск. Для обычного использования из терминала:

```sh
npm run build
npm start
```

При запуске через Life Hub открытая вкладка отправляет локальный heartbeat. После закрытия всех вкладок Life Hub может остановить сервис по `.runtime/web.pid` согласно политике `stopWhenBrowserIdle`.

Сервер слушает только `127.0.0.1`. Остановка — `Ctrl+C`. `PORT` и `ACTIVITY_DB` можно задать в `.env.local`; эти две настройки требуют перезапуска. В стандартной структуре `life-stack` SQLite находится в `../data/activity-checker/activity.sqlite`. SQL-миграции и рекомендованный каталог источников применяются при запуске. Отдельная команда: `npm run db:migrate`.

Без `start:setup -- --init` старый сценарий первого запуска создаёт четыре **вымышленных demo-записи**. Кнопка «Убрать примеры» удаляет их. При следующих запусках примеры не возвращаются. Демо не объединяются с реальными данными.

В ленте рядом с «не сербское название» доступен отдельный чекбокс **#Экскурсии**. По умолчанию он выключен; при включении остаются только карточки с явным тегом `Экскурсии` (без учёта регистра, необязательный `#` в сохранённом теге допустим). Название и описание не заменяют этот тег. Быстрый фильтр работает совместно с остальными фильтрами, не меняет выбор в «Все теги» и выключается кнопкой «Сбросить фильтры».

### Автоматическая архивация прошедших мероприятий

В **Источниках** есть настройка «Автоматически архивировать прошедшие мероприятия», включённая по умолчанию. Она сохраняется в SQLite (`settings`, ключ `auto-archive-past-events`) и действует при следующем запуске процесса сервиса и при ручном запуске любого источника группы **API Агрегаторы**, включая общий «Запустить».

При старте web-процесса архивация выполняется до приёма запросов по всем сохранённым географиям, в их часовых поясах. Агрегатор архивирует свою географию перед запросом и после импорта: прошедшие карточки, снова возвращённые источником, также уходят в архив. Используется та же операция, что ручная кнопка: завершение определяется последней известной датой (`endAt` или `startAt`); сегодняшние, продолжающиеся события и карточки без даты не затрагиваются. В `past_events_archive` сохраняются snapshot, личные оценки, избранное, заметки, feedback и provenance. Число архивированных карточек при синхронизации указано в предупреждениях результата.

Отключение опции не отключает ручную кнопку. Проверка подключения, планирование запроса, обычное открытие SQLite/CLI/MCP и синхронизация неагрегаторных источников не запускают автоматическую архивацию. TG-мероприятия используют свою текущую фильтрацию прошлых событий, как и раньше; эта настройка относится к canonical Event-карточкам штатной кнопки.

### Личный список ресторанов

В **Активностях → Рестораны** собраны Place-карточки с техническим тегом `restaurant`; в обычной вкладке «Места» они повторно не показываются. Карточка выводит тип кухни, Google-рейтинг и количество отзывов, когда они подтверждены публичным web-источником, отдельную ссылку Google Maps и кликабельный полный адрес. Старые статусы «Посещено · понравилось» / «Хочу сходить» не отображаются и не хранятся; закрытые места сохраняются с красной пометкой «Закрыто навсегда», чтобы история списка и исключения продолжали работать.

Старый персональный список из `content-checker` переносится идемпотентной командой:

```sh
npm run restaurants:import
```

Для каждой записи сохранён точный `knownIds.google_place`. Этот ключ участвует в canonical identity, поэтому повторный импорт и будущий Google Places discovery объединяются с существующей карточкой, а модель может исключать уже известные места по Place ID. Веб-рейтинги являются снимком на дату проверки: отсутствующие или неоднозначные значения остаются пустыми, а не угадываются.

## Первое использование

1. Откройте главную страницу и выберите Белград или Кишинёв.
2. В **Мой профиль** настройте интересы, языки, музыку и критерии четырёх групп.
   Предпочтения образца можно полностью заменить своими.
3. Нажмите **Запрос для модели**, отправьте скопированный запрос агенту или
   вызовите `$activity-recommendations`. Модель обновит доступные источники и
   сохранит подборку. Подключение Telegram расширяет покрытие; другие API опциональны.
4. Отмечайте избранное, скрывайте ненужное; отклонённые моделью события доступны
   отдельным списком по дням.

Описание ниже относится к сохранённым внутренним разделам и API.

Переключатель **Serbia** показывает все записи страны, **Belgrade** — город. Географию источника можно изменить только у адаптеров, которые действительно используют scope запроса. Кнопка **«Запустить»** в заголовке блока **API Агрегаторы** обновляет обычные агрегаторы, после чего открывает обязательный план подтверждения AllEvents. Значок запуска напротив каждой строки позволяет обновить только выбранный агрегатор; для AllEvents он также открывает подтверждение. MCP в общий или построчный запуск не входят. Источники уровня страны видны в scope Serbia; они не маскируются под городские.

Активности сразу разделены на вкладки **События → Рестораны → Сообщества → Места**; общей вкладки «Все» нет. Отфильтрованные карточки показываются одной непрерывной лентой без постраничной навигации. Для событий есть сегодня / неделя / эта и следующая неделя / выходные / период; даты сравниваются в `Europe/Belgrade`. Период «Эта и следующая неделя» начинается сегодня и заканчивается в воскресенье следующей календарной недели. События без подтверждённой даты не попадают в временные фильтры. Прошедшие события помечаются «прошло», автоматически не архивируются. Сообщества по умолчанию сортируются RU → international → local. В выдаче показываются неархивные записи.

Лента сначала отрисовывает 40 карточек и добавляет следующие порции при приближении к низу; без поддержки автоматической подгрузки остаётся кнопка «Показать ещё». Фильтры и счётчики учитывают весь каталог, а не только показанную порцию. При смене фильтра лента начинается заново; при оценке следующая карточка заполняет освободившееся место. Переключение вкладок не вызывает синхронизацию источников или перезагрузку базы.

Карточка события показывает отдельную плашку с полной локальной датой `YYYY-MM-DD`, вычисленным днём недели и, если оно известно, временем. Справа находятся независимое избранное «Хочу сходить» и взаимоисключающие оценки «Понравилось» / «Не понравилось»; дизлайк не удаляет карточку. Во время сохранения блокируется только выбранная карточка; оценка применяется локально после короткого затухания, без ожидания HTTP-ответа, и следующие карточки занимают освободившееся место. Разные карточки сохраняются независимо. При ошибке неудачное изменение откатывается и появляется сообщение; вся лента не перезагружается. Время отдельно в нижней строке не дублируется; отсутствующие части даты не подменяются служебными надписями. Социальные карточки показывают прямой кликабельный `@username` Telegram/Instagram либо ссылку Facebook. Для сообществ доступны фильтр и сортировка по структурированному размеру аудитории; неизвестный размер не исключает карточку. Demo-записи остаются в SQLite для разработки, но полностью исключены из списка, счётчиков и фильтров «Активностей». Категории, теги, языки и аудитории в фильтрах строятся только по реально заполненным значениям текущей географии; пустые фасеты не показываются. Вся панель фильтров раскрыта постоянно. Источники и теги выбираются мультиселектами с чекбоксами и общей опцией «Выбрать все»; их счётчики пересчитываются с учётом остальных фильтров. Для событий под поиском находится селектор «Оценка» с вариантами «Понравилось», «Не понравилось», «Избранное» и «Не оценено»; по умолчанию выбрано только «Не оценено». Рядом с «Оценкой» расположен компактный селектор «Даты»: календарь выбирает диапазон двумя кликами, показывает его в расширяющемся селекторе и поддерживает переход между месяцами, обратный порядок выбора и один день. Первый клик не меняет выдачу; второй применяет включительный диапазон, учитывающий пересечение с многодневным событием. Быстрые периоды и «Все даты» доступны внутри календаря. Следующее поле с иконкой часов принимает введённый вручную целый час от 0 до 23 и оставляет события, начинающиеся не раньше указанного локального часа. События без известного времени при активном фильтре исключаются. Чекбокс «не сербское название» в строке фильтров событий сразу после поля AI Score (на остальных вкладках — под поиском) по умолчанию включён и исключает заголовки с `Č`, `Ć`, `Đ`, `Š`, `Ž` и специфичными сербскими кириллическими буквами; обычная латинская `J` не считается признаком сербского текста. Записи без даты идут после датированных.

Зелёный блок фильтров дат убран. Язык и аудитория остаются в простой строке без плашки; избранное и часовой пояс перенесены к сортировке списка. В календаре сегодняшний день выделен светло-зелёным (дата определяется в часовом поясе выбранной географии); прошедшие дни серые и недоступны для выбора. Кнопка «Сбросить» снимает только фильтр дат и незавершённый выбор диапазона, не затрагивая оценку, часы и другие условия. Чипсы «Эта неделя» и «Эта и следующая неделя» продублированы после поля часов в общей строке под поиском: они используют те же периоды, что календарь, показывают активный выбор и обновляют диапазон в селекторе «Даты». Следом расположен фильтр «AI Score» с маленьким квадратным полем: целое число 0–10 задаёт минимальную оценку (например, `8` оставляет 8–10); карточки без AI-оценки при активном пороге исключаются. Очистка поля снимает ограничение; общий сброс фильтров также очищает AI Score. Ограничение действует только на обычные события и не меняет выдачу остальных вкладок.

На карточках обычных событий и Telegram-мероприятий AI-оценка подписана с префиксом: `AI 8.3/10`.

На странице «Правила фильтрации» нет кнопки сохранения: Enter в текстовом или числовом поле применяет заполненные правила к базе, Shift+Enter добавляет новую строку в список ключевиков. Переключатели включения правил применяются сразу. Во время запроса поля временно блокируются, повторные Enter не создают параллельных записей. После успешного сохранения и обновления выдачи на 3 секунды появляется уведомление «Изменения применены»; при ошибке показывается сообщение, а введённые значения остаются для повторного Enter. Верхняя вкладка «Активности» возвращает из правил в ленту без сброса её фильтров; то же делает логотип.

При обрыве соединения или пустом ответе при сохранении оценки клиент проверяет состояние этой карточки через GET: если изменение уже записано, повторной записи нет. При временных HTTP 502/503/504 допускаются до двух повторов того же явного значения, а не переключение оценки обратно. Лимит всей операции — 15 секунд. Остальные операции (импорт, платная синхронизация и т. п.) автоматически не повторяются. Не-JSON ошибки показывают понятное сообщение с HTTP-кодом вместо исключения JSON-парсера.

Иконка сброса рядом с «Все теги» снимает все пользовательские условия выдачи, включая поиск, оценку, избранное, даты и исключение сербских букв, и возвращает стандартную сортировку; тип карточек и география остаются прежними. Звёздочка рядом с timezone включает/выключает выдачу только избранных событий, ресторанов, сообществ или мест. Для событий она временно заменяет фильтр оценки, чтобы дефолтное «Не оценено» не скрывало избранное; при выключении восстанавливает прежнюю оценку. Остальные поисковые условия сохраняются.

Отдельная кнопка **«Правила фильтрации»** под архивированием показывает общее число отфильтрованных карточек и открывает шесть правил, которые применяются после нормализации каждого результата: прошлые события; Telegram-сообщества меньше заданного размера (по умолчанию 200; неизвестный размер пропускается); события Tickets.rs на перечисленных площадках или с ключевиками в площадке или названии; названия событий любого источника с заданными ключевиками; площадки и адреса событий любого источника с заданными ключевиками; теги карточек любого типа с заданными ключевиками. В списках можно использовать запятые и новые строки, сравнение не зависит от регистра и диакритики; для тегов символ `#` необязателен. Начальные исключения: точные площадки `Pan Teatar`, `Opera i teatar Madlenianum` и `Teatar Odeon`; ключевики Tickets.rs `pozorište` для площадки и `FEST 2026` для названия; ключевики названия для всех источников `tribute` и `Vaučer`; ключевик локации `Dečji`; ключевик тега `#For kids`. Обновление набора дефолтов один раз дополняет уже сохранённые правила, после чего пользователь снова может свободно их изменить. Каждое правило можно отключить или изменить. Карточки не удаляются: raw/provenance и canonical entity остаются в SQLite с признаком `filtered`, поэтому изменение правила немедленно пересчитывает всю выдачу.

Кнопка **«Архивировать прошлые события»** переносит события текущей географии, чья последняя известная дата раньше сегодняшней, в `past_events_archive` и удаляет их из рабочего списка. Счётчик рядом с кнопкой тоже рассчитывается только для выбранной географии, включая скрытые статичными правилами карточки. Событие, продолжающееся сегодня или позднее, и событие без даты не перемещаются. Архив содержит полный снимок canonical-карточки, источников и provenance; отдельного интерфейса восстановления пока нет.

На карточках обычных событий и Telegram-мероприятий известная дата окончания отображается полным интервалом: `2026-05-01 · Пт · 10:00 - 2026-05-10 · Вс · 20:00`. Каждый край форматируется в часовом поясе географии; для дат без времени часы не добавляются. Без окончания или при одинаковых краях остаётся одна дата. Сортировка и фильтрация дат не меняются.

Плашка **«Выходные»** находится в той же строке быстрых дат, сразу после «Эта и следующая неделя». Она выбирает субботу–воскресенье текущей недели по тем же правилам, что пресет «Выходные» внутри календаря, и синхронно обновляет селектор «Даты». На следующей неделе диапазон сдвигается к её выходным; сброс фильтров снимает выбор.

### Мой профиль

Профиль — единый источник персональных предпочтений для модели: общая информация,
языки, события, сообщества, музыка и артисты, дополнительные условия и четыре
поисковых промпта. Он хранится в SQLite, не содержит credentials и не требует
content-checker. Стартовый образец владельца можно полностью заменить своим.

Внизу «Дополнительно» — текстовые условия и описанные словами **действующие**
статичные фильтры с переключателями, а также исключённые Telegram-каналы.
Кнопка отключения условий образца снимает персональные машинные фильтры и
исключения каналов; текст и промпты нужно согласовать с выбранными предпочтениями.
Языковые пожелания — условия LLM-отбора, а не скрытый серверный языковой фильтр.
Сохранение профиля синхронизирует реальные настройки и делает старую ревизию
подборки неактуальной; уже сохранённый календарь автоматически не пересчитывается.

## MCP для веб-исследования и обычных агрегаторов

`npm run research:mcp` запускает stdio server `activity-checker-research` для
Codex и других MCP-клиентов. Работать из текущего checkout; Node 24+, существующие
npm-зависимости и уже инициализированная SQLite. `ACTIVITY_DB` задаёт путь к базе.
Сервер не запускает миграции, seed, обслуживание или сбор при подключении.

Доступные tools:

- `activity_web_search` — поиск публичных страниц событий через DuckDuckGo,
  с Bing RSS fallback; без API-ключа, импорта и JavaScript.
- `activity_web_read` — HTML/текст/JSON, ссылки и JSON-LD по публичному HTTPS URL;
  без cookies, авторизации, отправки форм или доступа к частной сети.
- `activity_aggregators_status` / `activity_aggregators_history` — свежесть и
  история существующих обычных источников выбранной географии, включая
  национальные источники той же страны.
- `activity_aggregators_plan` / `activity_aggregators_sync` — один сохранённый
  sourceId, существующий SyncService и прежние нормализация/dedup/provenance.
  Разрешены Tickets.rs, Afisha.rs, Belgrade Beat, Serbia Travel, AllEvents.
- `activity_archive_past_events` — прежняя архивация для запрошенного обновления
  или дайджеста, с сохранением личных данных.

Сначала прочитать status/history и синхронизировать нужные устаревшие источники
по одному. AllEvents требует plan и matching previewId/confirmed=true; запрос
на дайджест или бесплатное обновление уже разрешает этот sync после проверки
плана, повторный вопрос не нужен. Платные MCP-провайдеры не входят в этот сервер.
Максимум HTTP-запросов одного plan/sync: `maxRequests`, по умолчанию 60, до 100.
При достижении лимита запуск считается неуспешным, а не полной синхронизацией.

Публичный загрузчик проверяет адреса, фиксирует IP после DNS и проверяет TLS
по исходному hostname; перенаправления тоже проверяются. Локальные/служебные
IP, credentials в URL и посторонние домены для агрегаторов запрещены. HTML до
2 MiB, текст до 30 000 символов; HTTP-ответ агрегатора до 20 MiB. Внешний контент
недоверенный. Если нужен JS, логин, CAPTCHA или недоступный инструмент, агент
должен прямо назвать этот пробел в чате и не выдавать неполный поиск за полный.

Claw использует те же обработчики этого MCP в защищённом root-owned снимке
Agent Stack через внутренний MCP client и фиксированный Unix RPC. Это два
транспорта к одной бизнес-логике, а не вторая база или отдельные адаптеры сайтов.
Обновление snapshot — административное действие; изменение рабочего checkout
не подменяет код работающего изолированного агента.

Ключи для заготовки **не делают её рабочим подключением**. Даже при заполненных переменных Test / Sync недоступны, пока не реализован адаптер. Три Apify-источника, Telegram MTProto, Foursquare и официальный Google Places API (New) выше уже реализованы и больше не являются заглушками. PredictHQ и устаревший Facebook/ScrapeCreators полностью скрыты из интерфейса источников. Facebook-ссылки из найденных кандидатов направляются в рабочий Facebook Events · Apify. Неуспешный запрос, отсутствие разметки или credentials не имитируются пустым успешным импортом. У Ticketmaster пустой ответ допустим и означает отсутствие найденных событий.

Плашка **«Регистрация»** показывается только пока подключение, требующее аккаунта, ещё не готово. После появления зелёной галочки плашка скрывается. Публичные афиши и LLM Web обходятся без локальной регистрации.

Зелёная галочка рядом с названием источника означает, что подключение уже успешно прошло Test/Sync либо источник с настроенными credentials доступен модели через MCP. Поэтому она появляется у проверенных адаптеров, трёх Apify-источников (включая Google Maps и Facebook Events), Telegram MTProto, Foursquare и Google Places API (New). Раскрытая MCP-карточка показывает ссылки, ограничения и точные имена доступных tools, но не дублирует блоки подключения, credentials, статуса или Sync. Одна лишь реализация обычного непроверенного адаптера галочку не включает.

Системная группа **«Свои источники»** не показывается на вкладке источников. Ручной ввод и JSON-импорт выполняются через LLM и локальный API; служебный источник продолжает хранить их provenance в SQLite.

```sh
cp .env.example .env.local
```

Заполните нужные поля. **Ключи провайдеров перечитываются при запросах без перезапуска**; системные переменные окружения имеют приоритет над файлом. UI получает только признаки наличия ключей. Ключи не сохраняются в SQLite или браузере. URL источника с `token`, `apikey`, `key` и подобными параметрами запрещены; такой источник должен использовать отдельную серверную credential-настройку.

Ссылки и последовательность получения credentials находятся в раскрытой карточке источника и в [справочнике провайдеров](docs/PROVIDERS.md). Необязательные платные API не вызываются, пока модель не получит явное подтверждение запуска.

Вкладка **Источники → Другие** содержит Ticketmaster с ограниченным покрытием Белграда/Сербии. Bilet.rs и OpenStreetMap удалены из реестра и общего пакета адаптеров. Миграция `032_remove_retired_activity_sources.sql` удаляет их источники, raw-версии, попытки синхронизации, кандидатов и карточки без других источников; совместные карточки и архивы сохраняют независимую provenance. Перед применением к рабочей базе нужна проверенная WAL-aware копия. Остальные местные афиши находятся в API-агрегаторах.

Belgrade Beat представлен двумя карточками с разными назначениями. **Belgrade Beat** в API-агрегаторах при общей синхронизации последовательно читает `/events/this-week` и `/events/next-week`, выдерживая случайную паузу 2–3 секунды между запросами. Мобильная копия разметки не разбирается повторно; одинаковые canonical event URL схлопываются до записи в SQLite с сохранением самой ранней даты. Стабильный slug используется как внешний ID, поэтому повторный запуск обновляет существующую карточку или считается дублем, а не создаёт новую. **Belgrade Beat · LLM Web** остаётся отдельной точкой для поиска другой информации по публичным страницам сайта.

Вкладка **Найденные** содержит не найденные мероприятия, а кандидатов в новые источники. Activity Checker извлекает внешние ссылки из raw payload и текста импортированных/синхронизированных карточек, определяет вероятный тип (`telegram`, `instagram`, `facebook` или обычный сайт) и показывает, из какой записи пришла ссылка. «В источники» создаёт Source для последующей настройки, но обход автоматически не запускается. «Скрыть» помечает кандидата проигнорированным.

### Apify discovery и бюджет

В настройках Instagram, Facebook Events или Google Maps укажите до 30 поисковых гипотез, по одной на строку. Они не превращаются в 30 Actor runs: executor собирает все гипотезы одного провайдера в **один batch Actor run**. Перед Sync модалка показывает число гипотез, лимит на гипотезу, общий `maxItems`, ровно один Actor run и верхнюю оценку оплаты. Эти же ограничения отправляются в Apify как `maxItems` и `maxTotalChargeUsd`.

Рабочие ориентиры для планирования бюджета (актуальную цену всегда сверяйте на странице Actor):

| Actor            |      Примерная ставка | 100 результатов |
| ---------------- | --------------------: | --------------: |
| Instagram Search | ≈ $0.0027 / результат |         ≈ $0.27 |
| Google Maps      |      ≈ $0.004 / место |         ≈ $0.40 |
| Facebook Events  |    ≈ $0.013 / событие |         ≈ $1.30 |

Facebook заметно дороже, поэтому сначала используйте Instagram/Google Maps для discovery сообществ и мест, а Facebook — для небольшого числа наиболее ценных гипотез. MCP-tool `apify_status` валидирует token без запуска Actor. Apify-провайдеры не входят в общую синхронизацию и не имеют ручной кнопки Sync в строке.

Для research из терминала `npm run apify:tool -- ... --raw --output <file>` сохраняет dataset для проверки без автоматической записи всего шума. После ручного отбора `npm run apify:import -- --provider instagram --input <file> --id <username> ...` импортирует только перечисленные профили; запуск Actor при этом не повторяется.

Для вызова из терминала или агентом есть локальный tool. Без `--execute` он только печатает SearchPlan и стоимость:

```sh
npm run apify:tool -- \
  --provider instagram \
  --query "squash belgrade" \
  --query "squash serbia"
```

Явный `--execute` запускает один платный batch. Для пробной проверки используйте `--test-live --execute`: executor независимо от переданных чисел жёстко ограничит запуск **двумя оплачиваемыми результатами**. Token читается сервером из `.env.local`, не попадает в команду, UI, SQLite или output.

STDIO MCP запускается через `npm run apify:mcp` и публикует `apify_status`, `apify_instagram_search`, `apify_facebook_events_search` и `apify_google_places_search`. Все поисковые tools по умолчанию возвращают только бесплатный план; платный Actor стартует лишь при `execute=true`, а запись в SQLite дополнительно требует `store=true`.

### Google Places API (New) MCP и квота

Официальный Places API подключён рядом, а не вместо `Google Maps Places · Apify`. Ключ хранится как `GOOGLE_PLACES_API_KEY`; STDIO MCP запускается командой `npm run google-places:mcp`. Доступны `google_places_status`, `google_places_discovery_batch`, `google_places_text_search_ids`, `google_places_text_search_pro`, `google_places_text_search_enterprise` и `google_places_store_llm_ratings`.

В строке **Google Places API (New)** на странице источников отображаются два независимых локальных месячных счётчика: `Pro X/5 000` и `Enterprise Y/1 000`. IDs-only в эти короткие плашки не входит. Результаты сохраняют в discovery-реестре не только `placeId`, но и полученное название, поэтому уже исследованные места можно исключать без повторного платного запроса и без создания карточки активности.

Дефолтная стратегия `google_places_discovery_batch`: LLM передаёт до 30 текстовых гипотез; бесплатный `Text Search Essentials (IDs Only)` проверяет выдачу и записывает `placeId` в `google_places_discovered_ids`; уже существующие canonical IDs и ранее обогащённые IDs не тратят новый Pro-вызов. Только продуктивные запросы повторяются с Pro FieldMask стабильных полей карточки. Результат обязан иметь `displayName` и координаты; выполненный Pro-проход автоматически создаёт или обновляет локальную Place-карточку с названием, `googleMapsUri`, адресом, гео и типами. `minRating=4` применяется самим Text Search и настраивается в модалке источника с шагом 0.5.

Enterprise никогда не входит в default flow. Его отдельный tool требует одновременно `execute=true` и `confirmEnterprise=true`. Все поисковые tools по умолчанию dry-run. При явно подтверждённом Enterprise-поиске API-рейтинг и число отзывов записываются в карточку вместе с источником и временем проверки. Для независимого LLM-обогащения уже известных мест остаётся `google_places_store_llm_ratings`, который не вызывает Google API и не расходует квоту. Повторная Pro-синхронизация места не затирает сохранённый рейтинг.

`google_places_api_usage` хранит каждый отправленный запрос по billing month и SKU. Google сбрасывает месячные ступени первого числа в 00:00 `America/Los_Angeles`; локальные hard stops — 5 000 Text Search Pro и 1 000 Text Search Enterprise. IDs-only имеет unlimited free cap. SKU считаются Google независимо; дополнительный локальный вес `IDs=0`, `Pro=1`, `Enterprise=5` показывает Pro-equivalent нагрузку, но не смешивает официальные лимиты. Счётчик не видит запросы тем же ключом вне Activity Checker, поэтому Cloud quota остаётся обязательным вторым ограничителем.

### Telegram MTProto discovery и MCP

Telegram работает через пользовательскую MTProto-сессию, а не bot token. Установка изолированного Python-worker и одноразовый вход:

```sh
npm run telegram:setup
npm run telegram:auth
```

Второй шаг выполняется только в терминале: номер, код Telegram и 2FA-пароль не проходят через HTTP/UI и не сохраняются в `.env.local`. Сессия по умолчанию создаётся в `../data/activity-checker/telegram/activity-checker.session`, имеет права только текущего пользователя и не попадает в Git. Файл сессии эквивалентен авторизованному входу — его нельзя передавать или публиковать.

В настройках Telegram source укажите до 30 гипотез по одной на строку. В модалке Sync доступны:

- `searchPublicChats` через MTProto `contacts.search` — поиск публичных каналов и supergroups по названию/username;
- `channels.getChannelRecommendations` — похожие каналы для URL seed-канала либо общие рекомендации аккаунта.

Операции discovery выполняются последовательно в одной сессии с паузой 2.5–3.25 секунды. `channels.searchPosts` и `messages.searchGlobal` оставлены в worker как неактивный код на случай отдельного будущего решения, но не регистрируются и не вызываются ни из UI, ни из discovery MCP. Stars не расходуются.

CLI по умолчанию делает dry-run; внешний запрос требует `--execute`, запись в SQLite — дополнительного `--store`:

```sh
npm run telegram:tool -- \
  --query "squash belgrade" \
  --query "сквош белград" \
  --operation searchPublicChats \
  --max-items 20 \
  --execute
```

Два stdio MCP server запускаются отдельно:

- `npm run telegram:discovery:mcp` (старый alias `npm run telegram:mcp`) — `telegram_status`, `telegram_discovery_batch`, `telegram_search_public_chats`, `telegram_channel_recommendations`, query history и relevance marking, а также `telegram_discovery_filter_candidates`, `telegram_channel_info`, `telegram_channel_pinned_messages`, `telegram_discovery_recent_posts`, `telegram_search_channel_messages`, `telegram_group_topics`, `telegram_topic_posts`, `telegram_linked_chat_posts`, `telegram_post_comments`;
- `npm run telegram:monitoring:mcp` — `telegram_monitoring_status`, `telegram_monitoring_channels`, `telegram_monitoring_posts`, `telegram_search_channel_messages`, `telegram_bot_status` и `telegram_send_message_to_owner`.

### Отправка сообщения владельцу через Telegram-бота

`telegram_send_message_to_owner` отправляет текст только в заранее настроенный личный
чат владельца. Нужна явная просьба человека и `confirmed=true`; обычный сбор или
создание дайджеста сами по себе не разрешают отправку. Общие чаты и другие получатели
не поддерживаются этим инструментом. Боту нужно предварительно написать или нажать Start.

Настройте `TELEGRAM_BOT_USERNAME` (без `@`) и положительный `TELEGRAM_BOT_OWNER_CHAT_ID`
в игнорируемом `.env.local`. Токен можно передать через `TELEGRAM_BOT_TOKEN`, либо
указать `TELEGRAM_BOT_KEYCHAIN_SERVICE` и `TELEGRAM_BOT_KEYCHAIN_ACCOUNT` для существующей
записи macOS Keychain. Токен читается в память, не копируется между проектами и не
передаётся через аргументы CLI. Sandbox может блокировать Keychain: тогда тот же CLI
нужно запускать из обычного Terminal с доступом владельца, не вставляя токен в чат.

`telegram_bot_status` проверяет только наличие настроек, без токена и сетевых запросов;
`verified=false` не означает ошибку авторизации. Перед отправкой `getMe/getChat`
проверяют username бота, ID и тип личного чата. У одного бота с OpenClaw общие лимиты
Bot API; отправитель выдерживает паузу 1,2 секунды между отправками своего процесса/журнала,
но не координирует лимиты с другими приложениями. HTTP 429 останавливает отправку;
Stars и paid broadcasts отключены. Polling/webhook/OpenClaw не запускаются и не меняются.

Вход MCP: `{requestId: "<UUID>", text: "Текст и https://t.me/channel/123", confirmed: true}`.
Один `requestId` на одно сообщение, до 4000 символов UTF-16. HTTP(S)-ссылки и ссылки на
посты Telegram кликабельны; текст без Markdown/HTML, предпросмотр ссылок выключен.
Длинную подборку разбить по целым карточкам и сохранить UUID каждой части до отправки.

Для готового приватного файла `{ "messages": [<те же аргументы MCP>, ...] }`:

```sh
npm run telegram:send -- /absolute/path/messages.json
```

CLI использует тот же обработчик, что MCP. Журнал `.runtime/telegram-bot/` хранит хеш
получателя/текста и receipt без текста/токена, отдельно от live SQLite. `sent` с
`messageId` подтверждает принятие Telegram, но не прочтение человеком. Повтор того же
UUID/payload возвращает receipt без повторной отправки; другой payload отклоняется.
После потери ответа/crash статус `unknown`: остановиться и попросить владельца проверить
Telegram, не создавать новый UUID для слепого повтора. `rejected` содержит безопасный
код ошибки/`retryAfterSeconds`. Оставшийся после аварии `send.lock` не удаляется
автоматически: сначала проверить отсутствие отправки в процессе и сохранённые receipts.
Для новых MCP tools переподключите локальный monitoring MCP; облачный Personal Radar
этим изменением не обновляется. Все обычные monitoring/discovery операции остаются read-only.

LLM discovery идёт поэтапно: keywords → убрать уже имеющиеся/архивированные/скрытые/исключённые каналы → описание и подтверждённый размер → текущие закрепы без дат → свежие посты → при необходимости рекомендации от релевантных seeds. Семантический отбор выполняет модель, tools не имитируют автоматическую LLM-оценку. Все новые research-tools read-only и не сохраняют карточки. Закрепы возвращаются серверным `inputMessagesFilterPinned`, а не сканированием истории. В обоих MCP точечный поиск использует `messages.search` только внутри явного списка публичных каналов/групп; платный глобальный `channels.searchPosts` остаётся выключенным. Контракты и примеры: [docs/TELEGRAM_DISCOVERY.md](docs/TELEGRAM_DISCOVERY.md). Уже запущенные MCP-процессы нужно переподключить, чтобы появился новый набор tools.

В discovery можно получить темы форума и прочитать только выбранную, сообщив в чате найденные темы и причину выбора. Для релевантного канала связанный чат помогает проверить реальное общение, а комментарии конкретного анонса — запись, логистику и актуальные уточнения. Связь обсуждения проверяется через Telegram; auto-join/импорта нет. Эти контекстные tools применяют общий фильтр ответов, рекламы и минимума 51 символ, сохраняя исключённые каналы и keywords. «Общее» читается ограниченной выборкой истории с фильтрацией других тем; неполную выборку нельзя выдавать за отсутствие активности.

Monitoring читает `messages.getHistory` только для явно выбранных публичных каналов. Каналы можно передать как username/URL или как Community IDs из read-only `telegram_monitoring_channels`. `startDate`/`endDate` включительны в `timeZone` (по умолчанию `Europe/Belgrade`); `afterMessageIds` даёт incremental watermark, `beforeMessageIds` — курсор более старой страницы. На один monitoring batch принимается до 50 каналов. Запросы идут последовательно с базовой паузой 4 секунды и jitter 0–1.5 секунды; FloodWait не пережидается автоматически, а останавливает batch.

Каждый monitoring post содержит текст/дату/URL, edit date, author/sender, reply/forward/grouped IDs, views/forwards/replies/reactions, Telegram entities, hashtags, mentions, links, inline buttons, media type и доступные media metadata. Вычисляются простые signals (`hasExternalLink`, `hasTelegramLink`, `hasPrice`, `hasPromoLanguage`, `hasAdDisclosure`). До LLM можно детерминированно отсеять посты по views/длине, forward/reply/media-only, explicit ad disclosure, literal keywords, hashtags, link domains и media types. Это не семантический детектор рекламы: немаркированная нативная реклама выглядит как обычный пост и требует правил канала или LLM-оценки.

В monitoring по умолчанию включены `excludeReplies=true` и `excludeAdDisclosures=true`: исключаются сообщения-ответы, рекламные хештеги (`#реклама`, `#ad`, `#advertisement`, `#sponsored`), явные формулировки рекламной маркировки и идентификаторы `erid`. Пост с комментариями не исключается только из-за ненулевого `replyCount`. Цена билета, скидка или ссылка на регистрацию сами по себе не означают рекламу; немаркированные коммерческие предложения требуют точных keywords/domains или LLM-проверки.

`data/telegram-monitoring-filters.json` задаёт начальные literal keywords для двух подтверждённых повторяющихся спам-шаблонов (adult-реклама и «лёгкий заработок»). В **Посты → Настройки** можно изменить их: один ключевик на строку, буквальное вхождение без учёта регистра по тексту поста, включая хештеги. Настройки сохраняются в SQLite (`settings`, ключ `telegram-monitoring-settings`) и применяются до передачи постов в LLM; уже сохранённые карточки не удаляются. Дополнительные `excludeKeywords` MCP объединяются с сохранёнными, а не заменяют их. Низкоуровневый Node client/Python worker без MCP продолжают использовать файловые defaults.

В той же модалке задаются каналы, которые вообще не мониторятся: исключения применяются **до любых MTProto-запросов**, даже при явной передаче username/URL или Community ID. Первоначально выключены `serbia_padel`, `quizpleasebeg`, `oneamerikanopadel_beograd`, `Serbia`, `russkydombelgrad`; их можно включить обратно. `telegram_monitoring_channels` по умолчанию не возвращает выключенные каналы; `includeExcluded=true` показывает их для управления настройками. Если вся выборка выключена, posts возвращает пустой результат с `requestCount=0`. Комментарии и явная реклама по умолчанию исключаются; переключатели находятся в настройках.

Исключённые и архивированные каналы также не попадают в текущую ленту Telegram-мероприятий, её счётчик и текущий список проверенных каналов. Сохранённые карточки, оценки, feedback и исторические отчёты не удаляются: после снятия исключения/архива будущие мероприятия снова доступны. Keywords/reply/ad-фильтры по-прежнему применяются только к последующему мониторингу.

Telegram-сообщества (включая группы) вынесены в **Каналы**, остальные остаются в **Сообществах**. Вкладки идут подряд: **Сообщества → Каналы → Посты**. Отдельная вкладка **Посты** показывает счётчик актуальных сохранённых мероприятий для выбранной географии и позволяет фильтровать их по каналу, тексту и минимальному AI-score: одно числовое поле 0–10, например `8` оставляет оценки 8–10; очистка поля снимает ограничение. Фильтрация применяется сразу, как числовой фильтр времени в общей ленте. Telegram-вкладки отмечены иконкой самолётика. Migration 022 создаёт самостоятельные `telegram_events` и `telegram_event_reviews`; они не участвуют в общем списке Event, его экспорте и canonical AI-scoring. Monitoring остаётся read-only. После проверки по актуальному профилю отдельный review/import сохраняет только отобранные мероприятия с подтверждённой датой и причинами отбора. Карточка показывает источник, текущие теги канала, первую строку исходного поста (у Telegram нет отдельного поля title), до пяти предложений и ссылку на пост; раскрытие показывает полный исходный текст. Прошедшие мероприятия скрываются без удаления. Сводка помечает низкую отдачу каналов именно за проверенный период, не архивируя сообщества; удалённые каналы не показываются в текущей сводке.

В **Постах** дата мероприятия выделена компактной плашкой справа от названия, как в **Мероприятиях** (для интервала — обе границы), отдельно от даты публикации. Добавлены тот же календарь выбора диапазона, что в **Мероприятиях**, и сортировка по дате начала ↑/↓ либо AI-score ↓. Даты считаются в часовом поясе выбранной географии; фильтр включает протяжённое событие при пересечении диапазонов. Используются проверенные `startAt`/`endAt`, никогда не `publishedAt` в качестве запасной даты. Наблюдаемые паттерны анонсов и ограничения их интерпретации описаны в [docs/TELEGRAM_EVENT_DATES.md](docs/TELEGRAM_EVENT_DATES.md).

Ручной сбор всех активных сохранённых Telegram-сообществ с паузами 5–6.5 секунд: `node --import tsx scripts/telegram-monitoring-run.ts YYYY-MM-DD YYYY-MM-DD`. Снимок сохраняется в игнорируемой `.runtime/`. Проверенный draft импортируется явно через `scripts/telegram-events-import.ts snapshot.json reviewed-draft.json`; профиль защищён fingerprint-проверкой от изменения между анализом и записью.

В поле причины дизлайка под вводом доступны чипсы «балканская персона», «актуально только местным», «мода/одежда/украшения», «не релевантная музыка»: нажатие сразу сохраняет выбранный текст как причину (заменяя несохранённый черновик). Подсказка Enter/Esc убрана; Enter по-прежнему сохраняет текст. AI-review использует актуальные языки и тематические предпочтения из профиля; условия образца не являются обязательными для нового пользователя. Текущие AI-оценки автоматически не пересчитываются.

Карточки **tg событий** используют те же реакции, что общая лента: «Понравилось» / «Не понравилось» взаимоисключающие, повторный клик снимает оценку; избранное «Хочу сходить» независимо от оценки. Фильтр «Оценка» поддерживает «Не оценено» (по умолчанию), лайки, дизлайки и избранное. Карточка плавно уходит из «Не оценено» после отметки, но не удаляется; доступна через соответствующий фильтр. Сохранение и откат ошибок работают отдельно для каждой карточки, без перезагрузки ленты. Migration 023 хранит личные отметки отдельно от импортируемого текста в `telegram_events`; повторная проверка/import не сбрасывает их. Оценка относится к конкретному мероприятию, а не всему посту или каналу. Общие Event не изменяются; реакции на Telegram-мероприятия теперь учитываются в общем AI-preference summary с evidence ID `telegram:<id>`, но не добавляются в canonical candidates.

В обеих лентах при новом дизлайке слева от курсора появляется необязательное поле причины. Дизлайк записывается сразу, но карточка остаётся в выдаче, пока пользователь не отправит feedback (Enter/чипс) или не нажмёт вне окна, пропустив заполнение. Затем карточка плавно уходит, только если уже не подходит под текущие фильтры. Enter сохраняет текст (до 2000 символов) и показывает «Обратная связь записана»; кнопки подтверждения нет. Следующий дизлайк считается кликом вне предыдущего поля и открывает новое. Ошибка записи причины оставляет карточку и черновик на месте; прокрутка, изменение размера окна, перенос фокуса и Esc сами по себе не завершают feedback. Оценка сохраняется независимо и не ждёт комментария. Migration 024 добавляет личный атрибут `dislikeReason` к `entities` и `telegram_events`; он не перетирается Sync/review/import и сохраняется в архивном snapshot. При просмотре дизлайков причина видна на карточке. Снятие оценки не удаляет сохранённый текст, но AI-review учитывает его как отрицательную причину только при действующем дизлайке. Скилл использует явную причину для точного вывода, не подменяя отказ из-за времени/цены выводом о нелюбви к жанру. Изменение или очистка причины требует пересмотра summary при следующем AI-review.

Поисковые tools принимают `minParticipants`: каналы с известным меньшим числом участников отбрасываются worker-ом до результата, а неизвестное число пропускается. То же доступно в CLI как `--min-participants 200`. Полученное число сохраняется в `Community.memberCount` и используется интерфейсом и статичным правилом.

Дополнительные discovery MCP tools:

- `telegram_query_history` возвращает эффективность предыдущих keywords/seeds;
- `telegram_mark_query_relevance` записывает LLM-оценку: сколько результатов было действительно релевантно и сколько сохранено.

Каждый фактически выполненный поиск автоматически создаёт строки в `telegram_query_history`: `runId`, keyword или seed, operation, порог аудитории, число возвращённых, релевантных и сохранённых каналов. Это позволяет следующим discovery-проходам повторно использовать продуктивные формулировки и понижать нулевые/шумные запросы. CLI-эквиваленты: `--history`, `--sample-channel`, `--mark-run`.

Переиспользуемый профильный discovery-пул находится в `data/telegram-discovery-keywords.json`: 140 коротких русских, английских и сербских гипотез по сообществам, социальному спорту, IT/AI/product/startup и культурным активностям. Executor всё равно принимает не более 30 гипотез за один batch, поэтому пул нужно запускать последовательными проходами и сохранять только результаты после релевантностной фильтрации.

Расширенный профильный пул находится в `data/telegram-discovery-keywords-v2.json`. `npm run telegram:research` объединяет оба пула, выполняет последовательные batch по 30 запросов, пишет query history и сохраняет объединённый публичный результат в JSON без автоматического добавления сообществ. Например: `npm run telegram:research -- --limit 180 --min-participants 500`.

### Foursquare Places MCP и квота

Foursquare работает через актуальный Places Search API и локальный STDIO MCP `npm run foursquare:mcp`. Доступны два tools: `foursquare_status` без внешнего запроса показывает наличие ключа и остаток, а `foursquare_search_places` принимает до 10 ключевых гипотез. По умолчанию поиск возвращает только план; внешний вызов требует `execute=true`, запись найденных мест в SQLite — ещё и `store=true`.

На тарифе есть 500 бесплатных Pro-запросов за календарный месяц; каждая поисковая гипотеза расходует один запрос. После бесплатной ступени официальный тариф начинается с $15 за 1 000 вызовов. Локальный счётчик в `.runtime/foursquare-quota.json` жёстко блокирует 501-й запрос и не позволяет автоматически перейти к оплате. Ставки Apify и Foursquare собраны в `data/provider-quotas.json`; это проверяемый проектный снимок, а перед платным запуском всё равно следует сверять страницу провайдера.

Ключ `FOURSQUARE_API_KEY` хранится только в `.env.local`. MCP-инструкции требуют сначала вызвать `foursquare_status`, явно подтвердить живой поиск и никогда не обходить локальный hard limit.

### AllEvents

AllEvents работает с `https://allevents.in/belgrade/all`. Источник никогда не запускается автоматически или через общий Sync. Нажатие Sync сначала выполняет точный предварительный обход: открывает `/belgrade/all`, читает встроенную первую страницу и при необходимости идёт по пагинации до конца. В модалке после этого показаны точное число страниц, число уже выполненных запросов, карточки после дедупликации, даты, категории и количество raw-записей, уже находящихся в SQLite.

AllEvents не возвращает общий `total` в HTML, поэтому точное число нельзя получить только из одного ответа. Предпросмотр дочитывает страницы с случайной паузой 2–3 секунды и держит результат в памяти сервера 10 минут. Если даты/категории совпадают с HTML-страницей, встроенная первая страница используется напрямую; для других фильтров первая API-страница также загружается только один раз. Кнопка «Начать синхронизацию» не обращается к AllEvents повторно, а атомарно записывает этот кэш в SQLite. Изменение фильтров требует кнопки «Пересчитать точный план».

После трёх последовательных 401/403/429/503 адаптер прекращает обход и показывает ошибку. Полная исходная карточка сохраняется в `allevents_raw_events` и provenance, после чего отдельно нормализуется в canonical Event. Повторы между страницами удаляются по `event_id`; при записи в общий список также применяется детерминированное совпадение событий по known ID/URL либо точным названию, времени и городу (площадка — дополнительный признак). Максимум — 20 страниц; если к лимиту конец не найден, план не называется точным и просит сузить даты или категории.

Это недокументированный веб-интерфейс, а не партнёрский API. Личное некоммерческое использование само по себе не отменяет условия сайта: проверьте [условия AllEvents](https://allevents.in/conditions) и при необходимости получите разрешение. Реализация специально низкочастотная и не обходит блокировки.

## Pipeline и хранение

```text
Source → provider.sync → RawItem → provider.normalize → validation
       → deterministic matching → Entity + EntitySourceLink → UI
                                  ↘ SourceCandidate
```

SQLite работает через встроенный `node:sqlite`, без ORM и отдельного процесса БД. Все четыре canonical-типа используют общую таблицу `entities` с полем `type`, индексируемыми географией/датой и валидированным JSON остальных полей. Связи вынесены в `entity_relations`. Это упрощает unified view, миграции и импорт, сохраняя типы в TypeScript/Zod.

Миграция `021` добавляет производный JSON-кэш `entities.presentation`: готовую подпись даты, локальные дни/час, миниатюру даты, поисковый текст, признаки сербского заголовка/ресторана и форматированные размеры аудитории/числа отзывов. Кэш готовится сервером при импорте и редактировании; существующие записи заполняются при запуске без изменения оценок и `updatedAt`. Прямое изменение canonical JSON инвалидирует кэш; версия формата или изменение timezone также вызывают пересчёт. Относительные значения «сегодня»/«прошло» не сохраняются, чтобы не устаревать. Оценка обновляет только заданные поля одной записи и возвращает компактную карточку; raw/provenance читаются отдельно при открытии деталей.

- `scopes`: страны/города, timezone; прежнее техническое поле area ID не используется.
- `sources`: настройки источника, состояние, последний запрос и результат; без secrets.
- `source_items`: original payload/text, external ID, URL, checksum, даты. Изменённая версия сохраняется отдельно; повтор той же версии обновляет `fetchedAt`.
- `allevents_raw_events`: текущий полный raw-снимок карточки AllEvents, даты, category slugs, checksum и первое/последнее наблюдение.
- `google_places_discovered_ids`: бесплатные IDs-only находки и отметки последующего Pro/Enterprise enrichment.
- `google_places_api_usage`: локальный помесячный ledger вызовов Google Places по SKU, исходному query и весу.
- `entities.data`: canonical-данные карточек; пользовательские `favorite`, `reaction` (`like` / `dislike`), `skipped` и `skipReason` хранятся отдельными колонками и не перетираются синхронизацией.

В обычных мероприятиях и Telegram-постах кнопка «Пропустить» с залитой изогнутой стрелкой вправо ставит нейтральную отметку `skipped=true`. Карточка перестаёт подходить под «Не оценено», но остаётся на экране до отправки необязательного feedback или клика вне него. Можно написать причину/нажать чипс «дубль»; она хранится отдельно как `skipReason`, не как причина дизлайка. Найти карточки и отменить пропуск можно через «Оценка → Пропущено». Пропуск снимает лайк/дизлайк, новая реакция снимает пропуск; звёздочка независима. Пропуски и их причины не обучают рекомендации/summary; ранее учтённая снятая реакция лишь перестаёт быть сигналом. Migration 026 добавляет поля обеим таблицам, refresh/import и архив сохраняют их. При AI-review подтверждённые неоценённые дубли в текущем наборе помечаются пропуском с причиной «дубль», без удаления и изменения пользовательских оценок оригинала.
- `ai_event_preference_summary`: общая короткая выжимка предпочтений по пользовательской разметке событий, с ревизией и временем обновления.
- `ai_event_preference_evidence`: рассмотренные ID, snapshot лайка/дизлайка/звёздочки и индивидуальный вывод; сохраняется при переносе события в архив.
- `source_item_heads`: текущая версия каждой исходной записи; позволяет отличать повторный ответ от возврата источника к старой версии.
- `entity_source_links`: все источники каждой записи.
- `entity_keys`: детерминированные признаки идентичности.
- `duplicate_pairs`: сомнительные совпадения; пары событий со статусом `new` автоматически схлопываются, остальные типы и явно отклонённые пары сохраняются.
- `source_candidates`: найденные ссылки с исходной записью и состоянием new/accepted/ignored.
- `sync_runs`: результаты ручных синхронизаций, включая ошибки.
- `user_profile`: один локальный структурированный профиль предпочтений; без credentials.
- `past_events_archive`: полные снимки событий, вручную убранных из рабочего списка после завершения.

Нормализация объединяет варианты Beograd / Београд / Белград в Belgrade, приводит ISO timestamps к UTC, убирает tracking-параметры из ключей URL. Другие query-параметры, например ID билета, сохраняются.

Сопоставление: provider external ID, известные IDs, подходящий canonical URL, затем точные признаки события (название + время + город, дополнительно площадка) или места (название + адрес/координаты). События дополнительно схлопываются при одинаковых нормализованных названии и городе, если совпадает календарный день, отсутствует одна из дат либо совпадает непустая площадка. Уже существующие пары событий с плашкой «Дубль?» тоже схлопываются. Каноническая карточка получает самое раннее известное `startAt` и соответствующее ему `endAt`; provenance, provider keys, связи, избранное и заметки объединяются. Разные даты и разные непустые площадки остаются разными событиями.

Для Tickets.rs также действует обязательное правило серии: если canonical-содержимое карточек полностью одинаково, а различаются только `startAt`/`endAt`, URL и технические ID, они считаются повторными показами одного события. В рамках очередной синхронизации сохраняется ближайший актуальный показ, поэтому серия может перейти на следующую дату после исчезновения предыдущей из источника.

Для сообществ и мест сомнительная пара по-прежнему записывается в `duplicate_pairs` со статусом `new`, и обе карточки получают плашку. «Не дубль» переводит конкретную пару в `ignored`; ручное объединение сохраняет provenance, заметки и связи выбранной карточки и удаляет вторую canonical-запись. Для событий такие `new`-пары обрабатываются автоматически. GUID разных RSS-лент не считаются одинаковыми.

Ручные изменения полей защищены `overrides` и не затираются дальнейшим Sync. Избранное, архив, заметки и AI metadata сохраняются. Исчезновение записи из внешнего источника не удаляет её. Новые ссылки создают кандидатов, но не запускают обход или подключение автоматически.

Tickets.rs, Serbia Travel и AllEvents передают текущую дату в удалённый фильтр. Afisha.rs читает все страницы общего JSON-feed, который уже объединяет все разделы сайта. Для источников без удалённого фильтра прошлые карточки сохраняются в SQLite и помечаются статичным фильтром.

Afisha.rs может закрывать публичную страницу и JSON-feed проверкой Cloudflare (`HTTP 403`, `cf-mitigated: challenge`). В этом случае источник показывает конкретную причину «Cloudflare требует проверку браузера», а sync завершается ошибкой без импорта полученных страниц. Сохранённые карточки не заменяются пустой выдачей. Обычная автоархивация прошедших событий перед запуском агрегатора продолжает действовать. Автоматического обхода проверки, копирования браузерных cookies и повторов через другой адрес нет; для восстановления прямого sync требуется снятие блокировки сайтом.

## JSON-импорт и внешняя AI-обработка

Пример: [examples/import.json](examples/import.json). Машиночитаемая схема: [docs/import.schema.json](docs/import.schema.json), актуальная runtime-версия — `GET /api/import/schema`. Допустим массив, объект `{ "version": 1, "entities": [...] }` или JSON внутри Markdown fence. До 1 000 записей и 5 МБ за запрос.

Обязательные поля: `type` и `title`. Типы: `Event`, `Place`, `Community`. Неизвестные поля отклоняются. По умолчанию country=`RS`, city=`Belgrade`; для другой географии указывайте их явно. Даты: `YYYY-MM-DD` либо ISO 8601 с `Z`/offset. Date-only не превращается в выдуманное время. `url` — оригинал конкретной записи, `website` — сайт организации или сообщества. Неизвестные значения лучше пропускать.

```json
{
  "version": 1,
  "entities": [
    {
      "type": "Community",
      "title": "Подтверждённое название сообщества",
      "country": "RS",
      "city": "Belgrade",
      "url": "https://example.org/community",
      "languages": ["ru", "en"],
      "audience": "international",
      "tags": ["hiking"]
    }
  ]
}
```

Пакет валидируется целиком. Preview выполняет тот же pipeline в откатываемой транзакции; до кнопки «Импортировать» ничего не остаётся в БД. Сам импорт также атомарный.

AI-поля: `aiScore` (0–10/null; больше = релевантнее), `aiDecision` (`unknown|recommended|hidden`), `aiReason`, `aiTags`, `aiProcessedAt`. Новая карточка получает `aiScore=null`; встроенного LLM нет. Оценки может записывать внешний агент через `/api/ai-events-review/scores`, валидный JSON-импорт или `PUT /api/entities/:id`; последующий Sync их не перетирает. Миграция `020` один раз делит прежние оценки 0–100 на 10, включая manual overrides и архивные snapshot. Сортировка «По AI score» ставит заполненные оценки по убыванию, а `null` — после них. `hidden` — metadata; оно не скрывает записи автоматически без пользовательского фильтра. Экспорт JSON переносит canonical-поля, но не заменяет полный backup SQLite (не включает личные состояния, связи и raw-историю).

Скилл [`ai-events-review`](skills/ai-events-review/SKILL.md) сначала архивирует
прошлые события, обновляет summary личных реакций и оценивает будущие карточки
«Не оценено» по текущему `/api/profile` целиком. Языки, вкусы, исключения и условия
широкого включения находятся в профиле; в скиллах нет отдельной копии предпочтений.
AI-оценки не считаются человеческим сигналом. API проверяет актуальность карточек,
профиля и summary и атомарно сохраняет пакет. См. [контракт](docs/API.md).

### Профильный discovery через MCP и LLM

Скилл [`ai-mcp-discovery`](skills/ai-mcp-discovery/SKILL.md) подключается к запросам
вроде «используя MCP TG найди новые каналы про …», обогащению через Instagram/другие
MCP и «синкни Tickets.rs через LLM, затем отфильтруй/разметь». Автоматический выбор
включён; маршрутизация также закреплена в `AGENTS.md`. Обычный технический sync
без LLM-отбора не включает этот workflow. Текущие критерии релевантности берутся
из AI-review и профиля, без отдельной расходящейся копии вкусов.

До поиска модель обновляет общий summary пользовательских реакций (включая причины
дизлайков и снятые/изменённые отметки) и отдельный summary эффективности ключевиков.
Новая память в migration 025: `ai_mcp_discovery_summary`,
`ai_mcp_discovery_evidence` (рассмотренные query IDs, snapshots, fingerprints,
выводы) и `ai_mcp_discovery_query_history` для receipts MCP/агрегаторов без журнала.
Старая история Telegram и завершённых Google Places-запросов читается напрямую.
Новые/исправленные результаты снова попадают в pending; обновление выжимки и
evidence атомарно и защищено revision/fingerprint от параллельных изменений.
Summary синтезирует внешняя LLM при запуске workflow до планирования и после
завершённых batch, а не автоматический фоновый процесс.

Для платных и квотируемых MCP перед живым запуском нужно согласовать размер расходов
этого прохода и показать известные общий лимит, использовано, остаток и период.
Неизвестный баланс не означает ноль; локальные счётчики не видят внешний трафик.
Google Places учитывается отдельно по SKU; Enterprise нельзя включать по умолчанию.
Планирование/dry-run не заменяет согласования бюджета, старое разрешение не
распространяется на новый проход. Контракты — в
[reference скилла](skills/ai-mcp-discovery/references/api.md) и [docs/API.md](docs/API.md).

### Дайджест активностей

Последняя вкладка **«AI-дайджесты»** хранит снимки подборок в таблице `ai_digests`
той же SQLite. В ленте карточка свёрнута: период, краткий запрос, число уникальных
событий и источников. Название имеет вид «Тема · 5–9 октября»: сначала тема, затем период;
тот же формат применяется к старым карточкам при отображении без изменения снимков.
Вкладка и модалка используют локальную синюю палитру, включая заголовки, ссылки,
плашки дат/AI-score и состояния элементов управления. Нажатие открывает
полноэкранную модалку с фильтрами по датам,
минимальному AI-score и тегам (любой выбранный). События сгруппированы по дням;
протяжённые повторяются во всех днях пересечения, но считаются один раз. Таблица:
кликабельное название + описание/цена + хештеги в одной колонке, затем AI-score,
кликабельный источник и дата/диапазон в конце. Названия событий — синие, без жирного
начертания; хештеги и невыбранные теги-фильтры также синие. Теги сохраняются в JSON снимка;
старые карточки без тегов совместимы. Доступны сортировка
по окончанию периода (затем началу), актуальные подборки и архив. После окончания
периода карточки архивируются общей ручной/автоматической архивацией, с учётом
настройки автоархива. Исходные Event могут уйти в архив — снимок остаётся.
Скилл по умолчанию сохраняет карточку вместе с ответом; **«только в чате»** отключает
создание карточки.

Для явно запрошенной замены старый снимок можно удалить через
`DELETE /api/ai-digests/:id` с полным свежим `expectedDigest` из GET: изменившийся
снимок не удаляется, исходные мероприятия сохраняются. Сначала сохранить и проверить
новую подборку. Контракт описан в `docs/API.md`.

Скилл [`digest`](skills/digest/SKILL.md) вызывается как «дайджест на выходные»,
«куда сходить на ближайшей неделе» или «дай концерты международных групп на эти даты».
Он проверяет сегодняшнюю успешную синхронизацию каждого подключённого API-агрегатора,
обновляет недостающие источники и архивирует прошедшее, затем читает новые посты
активных Telegram-каналов и ищет события по текущим источникам LLM Web и сайтам
организаторов. Период публикаций отделён от дат мероприятий; локальные снимки и
завершённые границы чтения сохраняются в игнорируемом `.runtime/digest/`.

Отбор учитывает запрос, профиль и обновлённый summary личных реакций. Подтверждённые
неоценённые дубли получают `skipReason="дубль"`, рассмотренные события — обновлённые
AI-оценки; лучшие варианты выводятся в чате с датами, ссылками и объяснениями.
Вызов разрешает обычный сбор и сохранение событий; платные MCP требуют бюджета.
У Telegram текущая оценка называется `relevanceScore` (1–10), у canonical Event —
`aiScore` (0–10). Точные API, инкрементальный сбор и ограничения описаны в
[reference скилла](skills/digest/references/workflow.md).

## Ограничения первой версии

- JSON-LD читает только указанную страницу, без browser rendering и переходов по pagination. Наличие адаптера афиши не гарантирует полного покрытия сайта.
- RSS `pubDate` — дата публикации, не дата события. События без отдельного event timestamp сохраняются без даты.
- Повторяющиеся ICS-события пропускаются с предупреждением; обычные ICS учитывают TZID. JSON-LD timestamps без timezone оставляются пустыми с предупреждением.
- Не более одной сетевой операции одновременно. Повторный Sync одного провайдера — через 60 секунд; ограничения переживают перезапуск. Test не блокирует первый Sync. Автоматических повторов платных запросов нет.
- Нет map view, авторизации, cron, автоматического web crawler или LLM SDK.

## Публичное JavaScript-чтение

`npm run research:mcp` добавляет `activity_web_status` и `render=auto|static|browser`.
По умолчанию используется отдельный временный Chromium из `npm run browser:setup`:
публичный HTTPS, без личных cookies/логинов, форм, private network и WebSocket.

`ACTIVITY_BROWSER_SOCKET` оставляет необязательный существующий sidecar.
403/CAPTCHA и limited view раскрываются как ограничения; обход не выполняется.

`scripts/local-tool.ts research ...`; глобальный MCP необязателен.

Установка сохраняет embedded runtime, модель, расписания и остальные инструменты; native Codex plugin не включается.

## Ежедневный событийный дайджест OpenClaw

Дайджест читает новые анонсы мероприятий за последние 24 часа из активных
Telegram-каналов и бесплатных API-агрегаторов; веб-поиск — небольшой дополнительный
проход. Политические новости и AI-новостной раздел исключены. Подборка охватывает
сегодняшний вечер и ближайшие семь дней с полным ближайшим уикендом.

Миграция `029_digest_weekly_history.sql` добавляет `digest_weekly_history` в прежнюю
`activity.sqlite`. Таблица хранит наблюдения за фактами мероприятий, подготовленные
выпуски и подтверждения доставки; неделя — понедельник–воскресенье Europe/Belgrade.
Повтор одного сеанса в ту же неделю допускается только при проверенных существенных
новых деталях с пояснением изменения. Перепост, новая формулировка, AI-score и
обновление технического fetchedAt/updatedAt не считаются новым событием.

В начале нового запуска автоматически удаляется только история старше предыдущей
недели: остаются текущая и предыдущая недели. Полные `ai_digests`, мероприятия,
личные реакции и исходные посты этим не удаляются. Новая таблица входит в существующий
SQLite-бэкап Activity Checker; отдельной базы или автоматического push нет.

Бизнес-логика — `server/digest-weekly.ts`; закрытые MCP-операции и проверка доставки
scheduler предоставляются закреплённым deployment adapter Agent Stack. Транспорт
не регистрирует новых HTTP endpoints и не расширяет платных провайдеров.

## Рекомендации

В переключателе географии доступны только Белград и Кишинёв. Сохранённый выбор
прежнего флоу «Сербия» переключается на Белград. Миграция
`041_retire_serbia_flow.sql` переносит его настройки источников в Белград, сохраняя
raw-данные и историю; исторические снимки и личные состояния старого scope не
удаляются и не смешиваются с городскими подборками. Идентификатор `serbia`
остаётся внутренней совместимостью для чтения истории.

Вкладка **«Следующая неделя»** показывает полный следующий понедельник–воскресенье
в том же календаре и с теми же фильтрами, включая переход месяца и года. Снимки
трёх вкладок независимы. «Запрос для модели» на текущей неделе просит заполнить
обе недели одним потоком чтения источников без повторных вызовов.
При переключении географии выбранная вкладка периода сохраняется.
Верхний переключатель географии работает для всех вкладок; добавлен **Кишинёв**
(`chisinau`, MD, Europe/Chisinau). Снимки, скрытое, избранное и личные события
разделены по географии, критерии и профиль общие. Telegram-источники фильтруются
по country/city в Knowledge; источники Сербии не подмешиваются в Молдову.
Пул кандидатов для будущего мониторинга описан в
[исследовании источников Кишинёва](docs/research/chisinau-sources-2026-10-16.md);
само добавление города не запускает сбор и не подключает новых провайдеров.

Кнопка **+** справа сверху на вкладке недели добавляет **«Моё событие»**: день от сегодня до воскресенья, час начала, название и описание. Такие карточки розового цвета выделены фильтром «Мои события» и поддерживают избранное. Избранные карточки во всех вкладках и модалках отмечены жёлтой рамкой; в общем слоте рамка выделяет строку выбранного события. Корзина переносит их в «Скрытое», откуда событие можно восстановить; удаление в модалке слота не закрывает её. Личные события хранятся отдельно от снимков модели и переживают обновление подборки. Прошедшие дни исчезают из календаря; активные и удалённые личные записи автоматически очищаются после воскресенья по часовому поясу географии.


В основной навигации рядом с «Активности» и «Источники» появилась страница
«Рекомендации». Вкладка «Текущая неделя» показывает оставшиеся дни **от сегодня до
воскресенья** в общем почасовом таймлайне в часовом поясе выбранной
географии. Заголовок каждого дня содержит день недели, количество видимых событий
и дату. Четыре группы — спорт, прогулки, социальные события, концерты/выступления/фестивали —
различаются цветом и отключаются фильтрами непосредственно над календарём. Событие размещается только в день
начала; отображаемая длительность всегда один час, независимо от фактической.
На самой карточке показывается только точное время начала, без условного окончания;
один час относится к размещению в календаре.
Неизвестное время находится в последней строке «Без времени», после всех часовых
слотов календаря. Несколько событий одного
часового слота показываются списком названий в одной карточке; нажатие открывает
модалку с полными описаниями, временем начала и исходными публикациями.
Одиночная карточка показывает начало описания (первое предложение, до 220 символов
и трёх строк); нажатие на неё открывает полное описание в модалке.
Карточка содержит одну ссылку на исходную публикацию; отдельная ссылка на событие
и AI-score в интерфейсе не показываются. Тип обозначается иконкой: микрофон для
концертов/фестивалей, люди для социальных событий, дерево для прогулок и бицепс
для спорта. Такие же иконки находятся у фильтров. Иконка типа — справа внизу
карточки; верхняя строка содержит время начала, избранное и скрытие.
Фильтры и заголовки дней закреплены под основной
навигацией при прокрутке страницы. На узком экране календарь прокручивается
горизонтально вместе с заголовками дней. Рядом с фильтрами групп в поле «Начало с»
можно ввести минимальный час начала (`19` или `19:00`) либо выбрать его из списка
00:00–23:00. Фильтр оставляет события, начинающиеся в этот час или позже, включительно,
по часовому поясу географии;
«Все часы» или сброс возвращает всю подборку, включая события без точного времени.
При выбранном минимальном часе строки до него и строка без времени также скрываются.
Пустые начальные часовые строки также скрываются автоматически: календарь начинается
с самого раннего видимого события с известным временем во всей оставшейся неделе,
учитывая типы, скрытие и избранное. Более ранние строки возвращаются, когда появляется
подходящее событие. Если событий с точным временем нет, часовые строки не показываются.
Пустые строки после последнего видимого события также скрыты; внутренние промежутки
между событиями сохраняются. «Без времени» остаётся отдельной последней строкой.
Компактная общая галочка после типов событий выбирает все группы; когда выбраны
все, повторное нажатие очищает выбор. При частичном выборе она показывает «минус».
После очистки можно включать нужные типы по одному. Спорт обозначен жёлтым,
прогулки — зелёным.

Звёздочка в верхней строке карточки — отдельное избранное рекомендаций: события, на
которые планируется пойти. Повторное нажатие снимает звёздочку. В общем календаре
карточка остаётся и показывает подсвеченный значок. Компактная звёздочка после
«Начало с» переключает показ только избранных; учитываются текущие типы и время.
Избранное хранится в той же SQLite, общее для трёх вкладок в выбранной географии,
переживает перезапуск и новые подборки. Запланированные события остаются до
окончания, даже если новая подборка их пропустила. Скрытие имеет приоритет в
календаре, но звёздочка сохраняется для восстановления. Лайки canonical/Telegram
карточек и профиль от этого не меняются.

Значок перечёркнутого глаза скрывает отдельное событие, в том числе из общего
часового слота. Кнопка «Скрытое» рядом с «Подробнее» открывает список с восстановлением.
Список общий для трёх вкладок в выбранной географии, хранится в существующей SQLite
и переживает повторные подборки/перезапуск. Восстановление возвращает карточку даже
после её отсутствия в новом снимке. Скрытие не изменяет лайки/дизлайки.
При скрытии внутри модалки общего слота она остаётся открытой: обновляются список
и количество событий; после скрытия всех показывается пустой слот.
До анализа релевантности моделью skill использует детерминистический фильтр по
названию/источнику, прямой ссылке и локальной дате сеанса; новые Telegram-посты и
изменённое время в тот же день не обходят совпавшее скрытие. Прежние даты и истёкшие
события исключаются из календаря автоматически: проверка каждые 30 секунд и при
возвращении на страницу, также на стороне API. Истёкшее скрытое физически очищается
при запросах и раз в минуту, пока работает веб-сервис; исторические снимки сохраняются.

Обе опции доступны и на карточках вкладки «Концерты и фестивали 2026», в том числе
в модалках общих слотов. Звёздочка, скрытие и восстановление синхронизированы с
недельным календарём для одного сеанса в одной географии; годовая вкладка также
имеет кнопку показа только избранного.

Условия широкого включения сценических событий задаются в текущем профиле.
В образце владельца это русскоязычные гастроли даже при низком музыкальном match;
новый пользователь может изменить или отключить условие. AI Score остаётся
честной оценкой соответствия вкусу. Даты, проверка программы, дубли и скрытия соблюдаются.

Вторая вкладка — «Концерты и фестивали 2026»: будущие музыкальные концерты, известный
стендап, творческие встречи и фестивали (включая фестивали еды), сгруппированные по месяцам, с числом, днём недели и
временем. Прошедшие сеансы скрываются. Дата последнего обновления относится к
выбранной вкладке; пояснения к подборке открываются в модалке кнопкой «Подробнее»
рядом с этой датой. Обновление интерфейса само по себе не запускает модель или сбор.

«Мой профиль → Критерии» открывает четыре общих редактируемых промпта поиска/отбора, хранящихся
в существующей SQLite. Они применяются при следующем запросе к модели; страница
предупреждает, если снимок создан по старой ревизии. Новые снимки сохраняются
отдельно для scope и вкладки и не исчезают при архивации исходных Event.

Используйте [`activity-recommendations`](skills/activity-recommendations/SKILL.md):
«Обнови рекомендации недели и концерты 2026 года» или «Обнови только рекомендации
этой недели». Кнопка «Запрос для модели» копирует готовый запрос для отправки в чат.
Как и AI-дайджесты, рекомендации формирует внешняя модель через API/MCP;
встроенного LLM-запуска в веб-интерфейсе нет.

Skill читает актуальные промпты и профиль/feedback-summary, получает Afisha.rs
сначала через облачный Personal Radar MCP, обновляет подключённый AllEvents,
проверяет **все включённые публичные Telegram-каналы**
коллекции Personal Radar Knowledge `activity-telegram-channel-monitoring`
(в том числе отсутствующие в локальных Community), а также публичные группы
`activity-telegram-monitoring` с явным rich reader `telegram_read_messages`.
Для Кишинёва добавлены FRIENDS MD, VoleiNet и Центр 151;
[правила отбора](../personal-radar/workflows/chisinau-activity-monitoring.md)
содержат сведения об источниках. Язык программы для Центра 151, как и остальных
источников, сверяется с текущим профилем, а не с языковыми условиями владельца. Это отбор моделью при обновлении, не автоматический
серверный языковой фильтр. В активный веб-поиск Кишинёва входят также #diez и
E-Tineret: проверяются язык самой программы, возрастные ограничения и релевантность.
KEDEM и InterNations сохранены отключённым резервом в Personal Radar.
Skill использует hosted web search,
Meetup и другие актуальные LLM Web источники. Неполное чтение/ошибки отражаются в
снимке. [Порядок Afisha](skills/activity-recommendations/references/afisha-fallback.md):
облачный `afisha_read_events_batch` по `concerts`, `standup`, `festivals`, `cinema`
за объединённый период вкладок; при успехе локальный sync не запускается.
Это принятый охват, остальные разделы Afisha специально не добираются.
Только HTTP 403 от Afisha в облачном reader включает одну попытку локального sync.
При его неудаче используются валидные уже полученные данные, `@afishars` для
непокрытого текущего дня (Europe/Belgrade) и усиленный web search для будущих дат.
Если облачный tool недоступен или вернул другую ошибку, резервный сбор выполняется
без локального sync. Его жёсткое исключение кино раскрывается как ограничение
локальной ветки и не применяется к облачным карточкам автоматически.
Это правило также используется в дайджесте; другие источники продолжают обрабатываться.
После обновления в чате и `notes` перечисляются статусы облачного MCP, локального
sync и резервного сбора: успех, частично, блокировка, ошибка либо не запускался
с причиной. Успех облака не записывается как успех локального sync;
полнота веб-выдачи не гарантируется. Персональные исключения и языки берутся из профиля.

API: `GET /api/recommendations?scopeId=belgrade&kind=week|next-week|concerts-2026`,
`GET /api/recommendations/schema`, `POST /api/recommendations`,
`PUT /api/recommendations/settings`; подробности в [docs/API.md](docs/API.md).
Создание skill не выполняет реальный подбор. Расписаний по умолчанию нет.

Внизу модалки критериев находится раздел «Источники поиска мероприятий»:
свёрнутый раскрываемый список включённых публичных Telegram-источников из коллекций
Personal Radar Knowledge, подключённые агрегаторы и актуальные LLM Web источники
(Meetup, Eventbrite, Belgrade Beat). Исключения мониторинга подписаны в списке.
Дополнительные сайты берутся из ссылок на события/источники сохранённых подборок;
регистрационные Google Forms и карты в этот список не входят. При каждом открытии
модалки сервер заново читает все source-shards из manifest; при недоступном или
повреждённом Knowledge показывается предупреждение. Просмотр не запускает сбор,
не изменяет настройки источников и не вызывает внешние API.


### Концертные площадки из Knowledge

В «Источниках поиска мероприятий» страницы «Рекомендации» отдельно отображаются
концертные/стендап-площадки и организаторы из локальных коллекций Personal Radar
`belgrade-live-venues` и `belgrade-live-organizers`: приоритет P1/P2/P3,
специализация, ссылка и тип страницы (официальная афиша, соцсеть, агрегатор,
билеты или справка). Каталог ограничен Белградом; enabled/access/roles и география
проверяются при чтении. Недоступные/неполные индексы вызывают отдельное предупреждение,
сохраняя доступные каналы и обычные источники. Пустая программа сайта не считается
подтверждением отсутствия концертов.

API `GET /api/recommendations/sources?scopeId=belgrade` дополнительно возвращает
`venues` и `venueWarning`; прежние `telegram`, `other`, `additional` сохраняются.
Читаются все source/collection shards manifest и полные generated records,
без GitHub-запроса, catalog-sync, новой базы или импорта событий при открытии UI.
После редактирования Knowledge пересобрать его штатным builder; перезапуск
Activity Checker для обновления списка не требуется. Изменения backend/UI требуют
обычной сборки/перезапуска запущенной версии приложения.

Основной потребитель — `activity-recommendations`; общий
[концертный workflow](skills/activity-recommendations/references/concert-search.md)
переиспользуется `digest`. Он требует поиск по площадкам, артистам, жанрам и
оставшимся месяцам, проверку языка программы и lineup, сохранение поисковой памяти,
исключение скрытых событий до анализа. Редактируемые промпты и личные состояния
не изменяются. Каталог не запускает сбор/расписание сам.


Для проверенных русских страниц площадок Afisha каталог дополнительно возвращает
`venue.afishaVenueUrl`. В интерфейсе есть ссылка «Afisha · события площадки».
Концертный workflow использует `venue.afishaVenueUrl` в облачном Afisha reader
по тому же порядку этапов и дополняет web search, переиспользуя уже полученные
карточки и статус блокировки. Отсутствие облачного tool не блокирует подборку:
поиск продолжается через web. Скрытие до персонального анализа, пагинация и
дедупликация сохраняются; неполный доступ явно отражается в отчёте.


Источники Кишинёва подключены отдельными source ID: Fest.md, iTicket.md, Афиша мира,
AllEvents Chisinau, Afisha.md через anonymous renderer/sitemap, Sporter, Moldova Travel
и FRC. Пагинация и детали возобновляются из ignored runtime, iTicket сохраняет
отдельные сеансы. Поля coverage/unresolved раскрывают фактическое покрытие. Ограничения,
Telegram и web-first пул: [Молдова: коннекторы](docs/moldova-connectors.md).
